# 做影片：總流程

九個步驟、四個人審關卡，加上發布後的成效追蹤。每一步達到完成條件才能往下走。狀態記在 `videos/<id>/state.json`，用 `lib/state.py` 前進；沒有核准紀錄，它不讓你越過關卡。

## 1. 先看現在在哪

```bash
uv run python lib/state.py list
```

- 有影片停在某個狀態：照下表載入那一步的 skill，從那裡接續。已完成的產物（音檔、場景）有快取，不要重做。
- 沒有進行中的影片：先讀 `state/performance.md`（過去影片的成效和「下一支要改的事」；上一支做完後還沒跑頻道總覽的話，先照 `retrospective` 第 1 節跑），再從第 1 步「選題」開始。目標是增加訂閱數和觀看數。

## 2. 步驟

| # | 狀態 | skill | 做什麼 | 完成條件 | 之後 |
|---|---|---|---|---|---|
| 1 | 選題 | `select-topic` | 從觀念卡挑 2～4 個候選 | 候選都通過選題標準 | **關卡 1** |
| 2 | 規劃 | `plan-video` | 承諾句、骨架、暖身例子、**一張大圖的設計**、包裝 | 大圖有全景草圖；包裝通過自我檢查 | **關卡 2** |
| 3 | 腳本 | `write-script` | 逐句的顯示稿與唸法稿 | 片長在 3～15 分鐘內；字幕檢查通過 | — |
| 4 | 查核 | `write-script`（後半） | 查核員逐句對卡 | 每句都有標記；`claims.py` 通過 | 不過就退回第 3 步，最多 3 輪 |
| 5 | 旁白 | `narrate` | 合成旁白、回聽檢查、建立實測時間軸 | 每句都有音檔；回聽沒有問題 | — |
| 6 | 動畫 | `animate` | 逐場寫動畫、檢查、回看 | 版面、接縫、逐格檢查通過；整片逐秒回看兩輪 | — |
| 7 | 合成 | `assemble` | 混入品牌音樂與音效、打包 | 響度、長度、格數檢查通過 | — |
| 8 | 成片 | `assemble`（後半） | 成片自檢、審查包 | 所有程式檢查通過 | **關卡 3** |
| 9 | 發布準備 | `publish-prep` | 標題、縮圖、三語說明、上傳成私人 | 使用者定稿；已上傳成私人 | **關卡 4** → 使用者按公開 |
| — | 已發布 | `retrospective` | 第 7、28 天抓成效；回顧 | — | — |

**順序不能跳。** 兩個最貴的教訓：

- **規劃時就要定好「一張大圖」**。v001 沒有，成片重做了四版。
- **動畫一定在旁白合成之後做**，用實測的時間軸。v001 先用估算的時間軸做動畫，旁白合成後整批對不上。

## 3. 關卡怎麼交

每個關卡交一份**審查包**（`videos/<id>/review/gate<N>.md`），只放需要使用者判斷的東西；程式通過的檢查用一行帶過。範例：v001 的 `review/`。

| 關卡 | 審查包內容 | 使用者決定 |
|---|---|---|
| 1 選題 | 候選清單（來源卡、類型、預估長度、一句話重點、暖身例子與大圖的初步想法） | 選題、合併或拆集 |
| 2 規劃 | 承諾句、段落與時長、暖身例子對照表、大圖的全景草圖與鏡頭路線、每場的構想、2～3 組包裝 | 挑包裝，確認例子與大圖 |
| 3 成片 | 成片、要他決定的項目、被程式標記的項目、和規劃不同之處、沒經過人眼人耳確認的部分 | 用手機看完並回饋 |
| 4 發布 | 標題候選、縮圖、三語說明、上傳設定 | 定稿；同意上傳；自己按公開 |

使用者核准後：

```bash
uv run python lib/state.py approve <id> <N> --note "使用者的原話或摘要"
uv run python lib/state.py set <id> <下一個狀態>
```

使用者的回饋直接拿來修改這支影片，只重做受影響的步驟與場景，並把回饋和修改記在 `videos/<id>/design.md` 的最後面。

## 4. 和使用者合作

- **預期會來回好幾輪。** v001 的關卡 3 前後改了十幾輪（畫面、音樂、片尾、標題、縮圖）。每一輪都要把原因找出來、改完、說清楚改了什麼。
- **使用者的回饋常常是感受**：「粗糙」「吵」「沒活力」「好醜」「不夠有趣」。先找出具體原因再改：對照 v001、量測、逐格看。提案時給 3～5 個具體選項和一個建議，不要只問「你想要怎樣」。
- **使用者說「你來決定」「照你的建議」時就做完整**，並記下授權、來源和取捨。
- **使用者說「沒問題」之後，自己再回看一輪。**
- **Gemini 花費要報**：TTS 每句、文字生成每次都自動記進 `videos/<id>/gemini-usage.jsonl`。關卡 3 交成片和影片發布時，都附上 `uv run python lib/gemini.py cost <id>` 的總額。
- **每次交東西都寫清楚**：改了什麼、和上一版差在哪、哪些沒有經過人眼或人耳確認、要他特別看哪個時間點。
- **使用者偏好的風格**：清楚直白、口語、活潑；標題要有趣有節奏；畫面要專業精緻（3Blue1Brown 的水準），不要像投影片。

## 5. 失敗與中斷

- 查核改寫 3 輪、同一場渲染 3 次、同一句 TTS 3 次仍失敗：**停下來回報**。不換成投影片式的備援畫面，也不放寬規則。
- TTS 碰到每日上限不算失敗：程式會存檔，重置後跑同一個指令就從同一句接續。
- 卡在製作中途被修改了：不自動跟進。維持 `state.json` 記錄的 commit，並通知使用者。
- 對話太長：狀態都在檔案裡，可以開新對話，從 `state.py list` 接續。
