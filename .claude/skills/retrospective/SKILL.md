# 發布之後：成效追蹤與回顧

## 1. 成效追蹤（Claude 主動做）

**目標是增加訂閱數和觀看數**（使用者 2026-11-21）。成效數據是用來改下一支影片的，不只是記錄。

使用者 2026-11-16：成效「要由你自己 track」。使用者 2026-11-21：「每次完成一部 youtube 之後你也要去 track 過去已經發佈的影片的流量 從中學習來改善 video 的製作品質」。

### 每支影片做完之後（公開後、選下一題之前）

```bash
uv run python lib/analytics.py --overview         # 存成 state/performance.json，歷史附加在 performance.jsonl
uv run python lib/analytics.py --overview --show  # 之後再看一次，不連線
```

列出頻道最近 28 天的觀看與訂閱、流量來源、觀看最多的影片（含轉型前的舊程式教學影片），和我們每支影片從發布到現在的累計。

1. **曝光次數和點閱率由程式自己抓**：`--overview` 會讀 YouTube Reporting API 的 reach 報表（第一次會建立報表工作，約 2 天後才有檔案）。使用者 2026-11-21：「我可能不能每次都報給你，所以你可能要自己想辦法，或是參考其他指標就好」。**不要每次都向使用者要數字。** reach 還沒有資料時，用這些指標代替：瀏覽／推薦流量（BROWSE、SUGGESTED、SUBSCRIBER）佔比（YouTube 願意推、縮圖有人點）、平均看完比例、每千次觀看的新訂閱數。縮圖「測試與比較」的結果只在使用者主動提起時記下。全部記進 `state/performance.md` 的表格。
2. **讀出三件事**：哪支帶來最多訂閱、觀眾從哪裡來（搜尋、推薦、瀏覽）、點閱率和看完比例誰比較差。點閱率低就改包裝（標題、縮圖），看完比例低就改內容（看 d7 的流失位置）。
3. **寫進 `state/performance.md`**：日期、數字、你的判斷、下一支要改的一兩件事。選下一個題目時先讀它（`select-topic`），包裝時也讀（`publish-prep`）。
4. **規則**：影片不到 10 支之前，數據只當線索，不改規則；同一種現象出現在兩支以上才寫進 skill（第 3 節）。點閱率的目標只能用自己頻道的中位數，不要引用別的頻道的數字。

### 每次開始工作

```bash
uv run python lib/analytics.py --due
```

列出每支已發布影片的 d7（發布後第 1～7 天）、d28（第 1～28 天）狀態。數據延遲約 3 天，所以發布後第 10 天、第 31 天才算到期。標「到期」的就抓：

```bash
uv run python lib/analytics.py <id> d7        # 存成 videos/<id>/d7.json 並印出摘要
uv run python lib/analytics.py <id> d7 --show # 之後再看一次，不連線
```

- 只讀取。第一次或授權過期時瀏覽器會跳出授權頁，要使用者按同意；先告訴他。GCP 專案要啟用 YouTube Analytics API（`docs/youtube-upload.md`）。
- 曝光次數和點閱率不在 Analytics API 裡；`--overview` 從 Reporting API 的 reach 報表抓（GCP 要啟用 YouTube Analytics API 和 YouTube Reporting API）。
- 觀看數很少時 YouTube 不給留存曲線，程式會說明；記下來，d28 再看。

### 抓到之後要做的

1. **讀結果**：每場開頭和結尾的留存、每分鐘流失最多的場景、30 秒之後掉最多的幾個位置（程式已經對到場景和句子）。
2. **對照影片**：打開那幾句的腳本和動畫，判斷可能的原因。常見的：公式出現得太早、同一個畫面停太久、一段鋪陳太長、名詞沒解釋、轉場讓人以為結束了。
3. **講給使用者聽**：三到五句話。這支表現如何、觀眾在哪裡離開、你認為的原因、下一支打算怎麼改。原因是推測就說是推測。
4. **寫回規則**：只有在同一種流失出現在兩支以上，或原因很明確時，才改 skill（照第 3 節）。一支影片的數據只當線索。
5. 問使用者要不要 commit `d7.json`／`d28.json`。

## 2. 每支影片的回顧

使用者要求時做，或 d7 抓到之後一起做。保持簡短，只改確實需要改的地方。

1. 讀這支影片的 `state.json`（歷程、關卡回饋）、`design.md`（每一輪的回饋與修改）、`review/gate*.md`、`factcheck-program.json`、`d7.json`。
2. 找出：
   - 使用者的回饋裡，哪些是**通則**，以後每支都適用？
   - 同一類錯誤出現兩次以上的，改成程式檢查或 skill 規則。
   - 哪一步來回最多輪？能不能提前到更早的步驟解決（v001：視覺結構提前到規劃）。
   - 規則彼此衝突，或規則讓內容變差的地方。
3. 列出修改給使用者看，同意後才寫入並 commit。commit 訊息寫清楚改了什麼規則、起因是哪支影片。

## 3. 怎麼寫規則

skill 和 `CLAUDE.md` 是給**下一次從零開始、沒有任何對話紀錄的 Claude** 讀的。

- 寫「現在該怎麼做」加一句原因。原因最好是使用者的原話或具體發生過的事。
- **不寫版本演變**（「v2 改成…v3 又改成…」）。被取代的舊做法直接刪掉；歷程留在那支影片的 `design.md` 和 commit 紀錄。
- 同一條規則只寫在一個地方。細節放在對應步驟的 skill；`CLAUDE.md` 只放頻道定位、硬性限制、跨步驟的原則。
- 能用程式強制的，改 `lib/` 並附一個故意做壞的測試案例。
- 改完檢查一次：文件裡提到的檔案、函式、指令都還存在。
- **不得放寬硬性限制。** 想放寬，一定要明確問使用者。

## 4. 每 10 支影片：成效報告

讀各影片的 `d7.json`、`d28.json` 和 `fingerprint.json`，比較機制型與事實型、各種開場模式、片長、主題、標題寫法。

報告裡要寫明：樣本很小，主題熱門度會蓋過其他因素，所以差異只能當線索，不能當結論。交給使用者決定要不要調整選題或開場模式。
