# 發布後回顧

每週都會做一次，所以要**簡短**，只改確實需要改的地方。

## 做法

1. 讀這支影片的 `state.json`（歷程、關卡回饋）、`costs.md`、`review/gate*.md`、`factcheck-program.json`，以及渲染紀錄。
2. 找出以下幾類：
   - 使用者在四個關卡的回饋：哪些是**通則**，以後每支都適用？
   - 失敗與重試：同一類錯誤出現兩次以上，就該變成程式檢查或 skill 規則。
   - 額度消耗大的步驟。
   - 規則彼此衝突，或規則讓內容變差的地方。
3. 提出修改：
   - 改哪個檔、改成什麼、為什麼。
   - 細節規則寫進**對應的 skill**；`CLAUDE.md` 只放跨步驟的原則。
   - 同一條規則只寫在一個地方。
   - 能用程式強制的，就改 `lib/` 並附一個故意做壞的測試案例。
4. **先列給使用者看，同意後才寫入**，然後 commit。commit 訊息寫清楚改了什麼規則、起因是哪支影片。commit 紀錄就是規則的演變紀錄。
5. **回顧不得放寬硬性限制。** 想放寬，一定要明確問使用者。

## 每 10 支影片：成效報告

讀各影片的 `d7.json`、`d28.json`（成效抓取腳本產生）和 `fingerprint.json`，比較這幾個面向：

- 機制型與事實型；
- 各種開場模式；
- 片長；
- 主題。

報告裡要寫明：樣本很小，主題熱門度會蓋過其他因素，所以差異只能當線索，不能當結論。交給使用者決定要不要調整選題或開場模式。
