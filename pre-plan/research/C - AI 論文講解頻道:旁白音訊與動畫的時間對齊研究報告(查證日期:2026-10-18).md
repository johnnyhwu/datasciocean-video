# AI 論文講解頻道:旁白音訊與動畫的時間對齊研究報告(查證日期:2026-10-18)

我的建議是:**每一句旁白單獨呼叫一次 TTS,用「句子音檔的實際長度」決定場景長度,動畫時間一律寫成「相對於句子或字詞錨點」的形式,不要寫死成秒數**。Gemini TTS(包含透過 OpenRouter 呼叫)目前不回傳任何時間戳,所以只有需要「講到某個詞時觸發動畫」的地方,才另外跑強制對齊。

## TL;DR

- **Gemini TTS 不回傳時間戳。** 這點已經查證,透過 OpenRouter 呼叫也一樣:回應只有一段音訊。補救的辦法是「逐句合成」,這樣句子層級的時間會自動精確。字詞層級的時間,再用強制對齊工具(Qwen3-ForcedAligner-0.6B 或 Montreal Forced Aligner)以已知講稿對齊。
- **動畫端建議用 Remotion,不建議用 manim-voiceover。** 原因有三:Remotion 把「時長由資料決定」(`calculateMetadata()`)與字幕資料結構(`@remotion/captions`)都做成了一級功能;它是 React,跟 Claude Code 的相性好;逐場景渲染也容易隔離。manim-voiceover 在 2026-06-14 發布 0.4.0,已經原生支援 Gemini TTS,如果你想保留 3Blue1Brown 原汁原味的 Manim 畫風,它可以列為備案。但它在 PyPI 上仍標示為 Alpha,而且上一版停在 2024-09。
- **繁中強制對齊準確度:查不到台灣華語或繁中的正式評測。** 現有最好的普通話數據有兩筆:Montreal Forced Aligner(MFA)在 10,487 個音節邊界上的平均誤差是 15.59 ms;Qwen3-ForcedAligner 的中文 AAS,依 Qwen3-ASR 技術報告(arXiv 2601.21337)Table 9、以 MFA 標註為參考,原始語句是 33.1 ms,串接到 300 秒是 36.5 ms,但測試集大小未公開。YouTube 官方說明頁**沒有公布數值響度標準**,業界通用的 -14 LUFS 是第三方慣例。

## 摘要與結論(一頁版)

**名詞先講清楚:**
- **TTS(Text-to-Speech,文字轉語音)**:把文字合成成語音。
- **強制對齊(Forced Alignment,FA)**:已知講稿與音訊,算出每個字或詞的起訖時間。這跟「語音辨識(ASR,Automatic Speech Recognition,自動語音辨識,從音訊猜出文字)」是兩件事。
- **LUFS(Loudness Units relative to Full Scale,相對於滿刻度的響度單位)**:依人耳感知衡量平均響度的單位。
- **dBTP(decibels True Peak,真峰值分貝)**:考慮取樣間峰值的最高電平。

**結論與理由:**

1. **架構:「逐句 TTS → 句子時長 → 場景時長 → 逐場景渲染 → 串接 → 響度正規化」。**
   - 事實:Gemini TTS 不給時間戳,OpenRouter 的 `/api/v1/audio/speech` 只回傳原始音訊位元組流。
   - 推論:既然拿不到時間資訊,最便宜又最準的「句子級時間戳」,就是讓每一句成為一個獨立音檔,它的長度就是時間戳,誤差為 0,也不需要任何對齊模型。
2. **字詞級時間只在需要時才算。**
   - 3B1B 式動畫大多是「這句話講完前畫完這個圖」,句子級就夠了。
   - 只有「講到『注意力』這個詞時亮起某個方塊」這種情況,才需要字詞級。這時用強制對齊,而不是重新轉寫,因為講稿是你自己寫的,是已知的。
3. **局部重做的關鍵是「內容雜湊快取 + 相對錨點 + 場景獨立渲染」。**
   - 改一句旁白時,只有該句的音檔雜湊改變,所以只會重算該句音檔,再重新渲染它所在的場景,其他場景的影片檔直接沿用。
4. **動畫工具選 Remotion。** 它的官方文件直接示範用 Mediabunny 讀音訊時長,再在 `calculateMetadata()` 裡回傳 `durationInFrames`。注意:舊的 `getAudioDurationInSeconds()` 已被官方標為 deprecated。
5. **響度:最終混音的目標是 -14 LUFS integrated、-1 dBTP,用 ffmpeg `loudnorm` 兩段式處理。**
   - 事實:YouTube 官方說明頁只說「穩定音量(Stable volume)」預設開啟,沒有給 LUFS 數值。
   - 推論:-14 LUFS 是業界慣例,不是官方規範,但對語音類內容是安全值。

## Details

### 1. 常見的對齊架構

| 架構 | 做法 | 適用情境 | 缺點 |
|---|---|---|---|
| **A. 旁白先行,以時長驅動動畫(audio-first)** | 先生成旁白,量出時長,再把動畫拉伸或填滿到該時長 | 解說影片的主流做法;TTS 流程天然適合 | 動畫只知道「總長」,不知道句子內部的節奏 |
| **B. 動畫先行,旁白配速(animation-first)** | 先定好動畫秒數,再要求 TTS 調語速去塞進去 | 有固定節拍的片段(例如配音樂) | TTS 語速控制不精確;硬塞會讓語音不自然 |
| **C. 場景級對齊** | 每個場景一段音訊,場景長度等於音訊長度加前後留白 | 改一句只重做一個場景;最容易做到局部重做 | 場景內部的同步要靠估計 |
| **D. 句子級對齊(逐句 TTS)** | 每句一個音檔,句子邊界就是檔案邊界 | **本專案推薦**:不需要對齊模型,邊界誤差為 0 | 每句分開合成,句與句之間的語調可能不連貫(推論,見「已知的坑」) |
| **E. 字詞級對齊(強制對齊)** | 用 FA 工具把已知講稿對到音訊上,取得每個字或詞的時間 | 「講到某詞時觸發動畫」、逐字亮起的字幕 | 多一個模型依賴;中文斷詞、數字讀法、中英混排會產生對齊錯誤 |
| **F. ASR 轉寫取時間戳** | 用 Whisper 類工具或 Gemini 3.5 Transcribe 重新聽一次 | 沒有講稿時(例如真人錄音) | 轉寫出的文字可能和講稿不同,還得再對回講稿;時間精度不如 FA |

**事實**:WhisperX 論文本身就說明,Whisper 原生只有 utterance 級時間戳,而且「可能偏差數秒」,所以才要外掛 wav2vec2 音素模型做強制對齊。MFA 2026 年論文在英文 TIMIT 上的字詞邊界平均誤差:MFA 3.0 為 19.93 ms,WhisperX 為 110.04 ms,NeMo 為 78.24 ms,MMS 為 43.06 ms(TIMIT 共 630 名說話者、5.38 小時)。
**推論**:你手上一定有講稿,所以 F 架構只適合拿來「驗證」,不應拿來「定時」。

### 2. Gemini TTS 的時間戳現況與補救方法

**Gemini TTS 本身(事實):**
- Google AI Developers Forum 有一篇 2026-10-01 的 feature request 實測紀錄,測試日期 2026-09-30,測試介面是 `generateContent`。結果如下:
  - `gemini-2.5-flash-preview-tts`、`gemini-3.1-flash-tts-preview`、`gemini-3.8-flash-tts`、`gemini-3.8-flash-lite-tts` 四個模型的回應都「只有單一音訊 part」。
  - 設 `audioTranscriptionConfig.wordTimestamp = true` 會被靜默忽略。
  - `responseModalities: ["AUDIO","TEXT"]` 在 2.5 版會被拒絕,在 3.x 版會被忽略。
  - 官方語音生成文件完全沒有提到時間資訊。
- 2026-10-04 另有開發者附議,說自己也得「再跑一次語音轉文字」。截至 2026-10-18 看不到官方回覆。
- 輸出格式(官方文件):Gemini 3.8 TTS 的非串流請求回傳帶 RIFF 標頭的 WAV,規格是 24 kHz、單聲道、16-bit;串流請求回傳無標頭的原始 PCM(audio/l16)。`gemini-3.1-flash-tts-preview` 的非串流請求預設是無標頭的原始 PCM。

**透過 OpenRouter 呼叫(事實):**
- OpenRouter 於 2026-05-01 推出 `/api/v1/audio/speech`,2026-07-07 更新公告。這個端點相容 OpenAI Audio Speech API,回應是「原始位元組流」,格式為 MP3 或 PCM。
- OpenRouter 的 TTS 模型集合頁列有 Gemini 3.8 Flash TTS、Gemini 3.1 Flash TTS Preview、Gemini 3.8 Flash Lite TTS。
- 依 OpenRouter 文件鏡像(mintlify 子網域,屬二手來源),不指定 `response_format` 時預設是 PCM。
- **推論**:回應本體就是音訊位元組,不存在放時間戳的欄位,所以透過 OpenRouter 一樣拿不到時間戳。拿到 PCM 時要自己知道取樣率(Gemini 是 24 kHz),否則量出來的時長會錯。建議明確指定格式,並轉存成 WAV。

**繁體中文準確度(請注意分母):**
- **台灣華語或繁中的正式強制對齊評測:查不到**,TAT、MATBN、Common Voice zh-TW 都查不到時間戳評測。
- 最接近的是 arXiv 2409.07891(2024):用 MFA 對齊台灣華語自發語料(118,592 個單字詞 token),作者人工抽查 10% 的 token,在子音與母音交界處「約 90% 落在 20 ms 內」。這屬於非正式抽查,抽查數量和 MFA 版本都沒有寫明。
- **普通話 MFA**:Wu 等人 2023 年發表於 *Humanities & Social Sciences Communications* 的研究,有 33 名說話者、4,096 個檔案(216 分鐘),隨機抽 1,120 檔評估:
  - 音節邊界:10,487 個邊界,平均誤差 15.59 ms(標準差 30.41),73.49% 落在 25 ms 內。
  - 片語邊界:3,944 個邊界,平均 22.49 ms,65.57% 落在 25 ms 內。
  - 限制:使用的是 MFA v1.0;人工參考答案是「修正 MFA 輸出」得來的,誤差可能被低估;語料應為中國普通話(推論)。
- **Qwen3-ForcedAligner(Chinese,AAS 越低越好)**:
  - 以 MFA 標註為參考:原始語句 33.1 ms(NFA 109.8,Monotonic-Aligner 161.1);串接到 300 秒的長音訊 36.5 ms(NFA 235.0,Monotonic-Aligner 1742.4)。
  - 以人工標註為參考:平均 32.4 ms(NFA 101.2,Monotonic-Aligner 141.3)。不過 Qwen3-ASR 技術報告把這個 32.4 ms 列為人工標註集的「Avg.」,沒有標成中文專屬,所以不應算進中文的區間;說人工標註集是中文內部資料的,是配套論文 arXiv 2601.18220。
  - **測試集大小未公開**。人工標註集是內部資料;中文訓練來源(AISHELL、WenetSpeech 等)都是中國大陸語料,也沒有提到台灣資料。
  - AAS(Accumulated Average Shift,累積平均偏移)是預測時間戳與參考時間戳的平均絕對差。要注意它的預測落在 80 ms 格點上:arXiv 2601.21337 §3.4 原文寫「multiplying each index by 80ms recovers the actual predicted timestamps」,最多 3,750 個類別,對應 300 秒。
- **推論**:你的音訊是 TTS 合成的乾淨語音,比上述評測用的真人錄音容易對齊,所以 30 ms 左右的誤差在 30 fps 下大約 1 幀,對動畫觸發來說綽綽有餘。真正的風險不在毫秒級誤差,而在「TTS 念錯、漏念、數字或英文的讀法跟講稿不一致」,那會讓對齊整段錯位。

### 3. 動畫工具整合與維護狀態

**manim-voiceover(事實,PyPI):**
- 0.4.0 版於 2026-06-14 發布,上一版是 0.3.7(2024-09-29)。
- 需要 Python ≥3.11,開發狀態標示「3 - Alpha」,有 3 名維護者。
- extras 包含 `gemini`、`openai`、`azure`、`elevenlabs`、`transcribe` 等。
- README 把 Gemini TTS 列為「AI 語音首選(Recommended)」,並說字詞級觸發靠 OpenAI Whisper 實現(bookmark 機制)。
- Snyk 在 2025-11 判定它「Inactive」,這個判斷已被 0.4.0 推翻。
- GitHub issues 有 #113「手動 bookmark 時間」(2025-04)、#121「支援 Kokoro TTS」(2025-11)等未決議題。
- 社群另有 manim-voiceover-fixed、manim-voiceover-enhanced、kokoro-manim-voiceover 等 fork,以及給 ManimGL(3b1b 原版 Manim)用的移植版。
- **推論**:它的 Gemini 整合應該是直連 Google API,不經 OpenRouter。這點我沒有讀原始碼,**未查證**。如果你堅持走 OpenRouter,可能要自己寫 SpeechService。

**Remotion(事實,官方文件):**
- **音訊時長**:`@remotion/media-utils` 的 `getAudioDurationInSeconds()` 已標 deprecated,官方建議改用 `getMediaMetadata()`,或用 Mediabunny 的 `input.computeDuration()`。`@remotion/media-parser` 的 `parseMedia()` 也已 deprecated。
- **時長驅動**:在 `<Composition>` 傳入 `calculateMetadata()`,回傳 `durationInFrames: Math.ceil(durationInSeconds * fps)`。它在渲染前只跑一次,結果會覆蓋 Composition 上的預設值。多段素材可以用 `<Series.Sequence>` 依序排列,把各段時長加總。
- **字幕**:`@remotion/captions` 定義了 `Caption` 型別 `{text, startMs, endMs, timestampMs, confidence}`,並提供 `parseSrt()`、`serializeSrt()`、`createTikTokStyleCaptions()`(用 `combineTokensWithinMilliseconds` 分頁)。轉寫來源可以是 `@remotion/install-whisper-cpp`、`@remotion/whisper-webgpu`、`@remotion/openai-whisper`、`@remotion/elevenlabs`。
- **版本**:media-utils 文件頁的安裝指令假設版本是 v4.0.532。確切的發布日期**查不到**。
- **推論**:Remotion 的 `Caption` 型別可以直接當作你整條流程的「時間戳中介格式」:FA 的輸出轉成 `Caption[]`,同一份資料同時驅動動畫錨點和輸出 SRT。

### 4. 改一句旁白時,把影響限縮在該場景的設計模式

1. **內容定址快取(content-addressed cache)**:音檔檔名等於 hash(句子文字 + voice + 模型 + style prompt + 語速)。文字沒變就不會重新呼叫 TTS。
2. **場景時長由下而上計算**:場景時長 = 前置留白 + Σ(句子時長 + 句間停頓) + 後置留白。改一句只會改變那個場景的總長。
3. **動畫只引用錨點,不寫絕對秒數**:例如 `at: {sentence: "s3", word: 2, offset: +0.1s}`,或「在 s2 到 s4 之間完成」。時長一變,錨點會自動重新解析。
4. **彈性時段(slack / elastic segments)**:每個場景保留可伸縮的「停留」動畫,比如靜止畫面、緩慢鏡頭推移。旁白變長或變短時,只伸縮這一段,不去動精心調好的轉場。
5. **場景獨立渲染,最後串接**:每個場景輸出一個獨立影片檔,依賴關係是「場景 → 它的句子音檔雜湊 + 場景程式碼雜湊」,只有雜湊變了才重新渲染,最後用 ffmpeg 串接。
6. **全域時間軸只在串接時計算**:字幕的絕對時間 = 場景起點 + 場景內相對時間,在最後一步才算。改一句只會讓後續字幕整體平移,不需要重新對齊。
7. **轉場放在場景內部或邊界的固定長度上**:避免跨場景的動畫依賴前一個場景的長度。

(以上 7 點是一般軟體工程模式的應用,屬推論,不是來自特定來源。)

### 5. 繁體中文字幕(SRT/VTT)

- **產生方式**:句子級時間戳加上場景偏移,得到每句的絕對起訖時間;再依下面的規則切成 cue,輸出 SRT 或 VTT。Remotion 的 `serializeSrt()` 可以直接用。SRT 的時間格式是 `00:00:01,000`(逗號),VTT 是 `00:00:01.000`(句點),兩者的差別主要在這裡。
- **斷行規則參考(事實,Netflix 繁中 Timed Text Style Guide)**:
  - 每行 16 字;必要時可放寬到 18 字。
  - 成人節目閱讀速度上限每秒 9 字。
  - 「通常保持一行,超過字數限制才換行」。
  - Netflix 的另一頁 FAQ 說:非 Originals 內容的繁中自動 QC 上限是每行 23 字,Originals 是 16 字。
- **推論建議**:
  - 每個 cue 最多 2 行,每行 ≤16 個全形字。
  - 優先在標點(,。;:?!)處切,其次在詞界切。中文斷詞可以用 FA 工具附帶的斷詞結果。
  - 不要在「數字+單位」「英文單字」「專有名詞」中間切。
  - 每秒 ≤9 字,超過就把 cue 拉長或拆開。
- **中英數混排的常見問題(推論)**:
  1. 字數計算要用「顯示寬度」,不能用 `len()`:半形英數約算 0.5 字。
  2. 中英之間是否加空格要全片統一。
  3. 字幕文字應該是「講稿原文」,不是 ASR 結果,否則會出現簡體字或錯字。
  4. 講稿裡的「GPT-4」「10^9」「2.5 倍」等,TTS 的念法可能跟字面不同。建議維護兩份文字:一份是「念法稿」(餵給 TTS 和 FA),一份是「顯示稿」(上字幕),兩者以句子 ID 對應。
  5. 對齊工具的發音詞典或訓練資料可能偏向簡體:MFA Mandarin 這一半仍是推論;Qwen3 這一半有原文佐證,arXiv 2601.21337 說 ForcedAligner 用的是「pseudo-timestamp labels generated by the Montreal forced aligner (MFA)」,AuT 編碼器的預訓練資料是「approximately 40 million hours of pseudo-labeled ASR data, where the majority is in Chinese and English」。因此可以先用 OpenCC 把繁體轉成簡體再對齊,再依字元索引映射回繁體。繁簡多數是一對一,但要檢查少數一對多的字。

### 6. 音量與響度

- **YouTube 官方(查證日期 2026-10-18)**:
  - 「Control video volume on your device」說明頁:「穩定音量(Stable volume)預設開啟」,它會「持續調整音量以減少變化」;不是所有影片都有這項功能;音樂內容會關閉;開啟「人聲增強(Voice boost)」時會自動關閉。
  - 「YouTube recommended upload encoding settings」說明頁:音訊編碼 AAC-LC 或 Opus,取樣率 48 kHz,立體聲 384 kbps、單聲道 128 kbps。
  - **這兩頁都沒有公布 LUFS 數值。** APU Software 的整理也指出:YouTube 公開說明「沒有定義數值的母帶或上傳目標」。
- **業界慣例(第三方,不是官方)**:-14 LUFS integrated、真峰值 -1 dBTP,而且 YouTube「只調降、不調升」。這些說法常見於 criticallisteninglab、rswaver 等網站,屬第三方觀察。
- **ffmpeg 自動化(兩段式)**:
  1. 量測:`ffmpeg -i mix.wav -af loudnorm=I=-14:TP=-1:LRA=11:print_format=json -f null -`,從 stderr 解析 JSON 中的 `input_i`、`input_tp`、`input_lra`、`input_thresh`、`target_offset`。
  2. 套用:`loudnorm=I=-14:TP=-1:LRA=11:measured_I=…:measured_TP=…:measured_LRA=…:measured_thresh=…:offset=…:linear=true`,最後加 `-ar 48000`。
  3. 驗證:`ffmpeg -nostats -i out.mp4 -af ebur128=peak=true -f null -`,讀取 Integrated 與 True peak。
  - 單段式 loudnorm 不建議用:FFmpeg Micro 的 Javid Jamae(2026-08-13)寫道「Single-pass loudnorm is a live estimator and routinely lands a full LU off target; two-pass is what makes files match each other.」它還會產生抽吸(pumping)感。批次處理可以用 `ffmpeg-normalize`。
- **推論建議**:
  - 先對每個句子音檔做輕量的峰值或響度一致化,讓逐句合成的音量不會忽大忽小。
  - 正式的 loudnorm 只對最終整片混音做一次,不要逐場景做,否則場景間會有響度跳動。
  - Gemini 輸出是 24 kHz 單聲道,最終要重新取樣到 48 kHz,以符合 YouTube 建議。

## 推薦的對齊架構(資料流)

```
[0] 講稿 script.yaml(場景 → 句子;每句有 id、display_text、speak_text)
   ↓
[1] 逐句 TTS(Gemini via OpenRouter /audio/speech,明確指定格式)
    → audio/{hash}.wav(快取:hash = 文字+voice+model+prompt)
   ↓
[2] 句子後處理:轉成 WAV 48k、修剪頭尾靜音、量測時長(ffprobe)
    → timings/{hash}.json {duration_ms}
   ↓
[2b] 驗證:ASR 回聽(faster-whisper 或 Gemini 3.5 Transcribe),和 speak_text 比字元錯誤率(CER),超過門檻就重新生成
   ↓
[3] (僅限有字詞觸發需求的句子)強制對齊:Qwen3-ForcedAligner-0.6B 或 MFA
    → words/{hash}.json(轉成 Remotion Caption[])
   ↓
[4] 場景時長計算:Σ句長 + 停頓 + 彈性時段 → scene_manifest.json(含每句的場景內起點)
   ↓
[5] 逐場景渲染(Remotion calculateMetadata 讀 manifest;動畫綁錨點)
    → scenes/{scene_id}_{hash}.mp4(只有雜湊變了才重渲)
   ↓
[6] 串接 + 混音(ffmpeg concat;音訊在這一步才統一編碼成 AAC)
   ↓
[7] 響度:loudnorm 兩段式 → -14 LUFS / -1 dBTP;ebur128 驗證
   ↓
[8] 字幕:場景偏移 + 句子時間 → 依 16 字/行、9 字/秒切 cue → SRT/VTT(用 display_text)
```

**理由**:[1] 加 [2] 免費提供精確的句子邊界,[3] 只在必要時才付出成本,[4] 加 [5] 把變動隔離在單一場景,[8] 用顯示稿,避免 ASR 錯字上字幕。

## 已知的坑

1. **逐句合成的語調斷裂(推論)**:每句獨立生成,句尾語調和句間呼吸可能不自然,同一個 voice 在不同請求間的音色或語速也可能飄移。對策:用固定的 style prompt;改成「每場景一次合成」再用 FA 切句也可以,但那樣就要依賴 FA 的準確度。建議先做 A/B 試聽再決定。
2. **TTS 漏念或亂念**:對齊工具假設音訊和講稿一致,一旦漏字,整段對齊都會錯位。所以 [2b] 的回聽驗證不能省。
3. **PCM 沒有標頭**:OpenRouter 不指定格式時預設 PCM(二手來源),Gemini 3.1 也預設原始 PCM。用錯取樣率會讓時長算錯 2 倍以上。
4. **頭尾靜音**:TTS 音檔常帶前後靜音,要先修剪,再自己決定停頓長度,否則場景節奏會不穩定。
5. **幀數捨入累積**:每個場景各自 `Math.ceil` 的話,長片會累積誤差。用「累計時間再換算成幀」的方式計算,讓字幕和畫面不會越來越偏。
6. **AAC 串接延遲**:每個場景各自編碼成 AAC 再串接,可能在接縫產生微小的空隙或偏移(推論)。建議各場景的音訊保持 WAV 或 PCM,到最後一步才統一編碼。
7. **Whisper 時間戳不可直接用**:WhisperX 論文指出 Whisper 原生時間戳可能偏差數秒;在英文 TIMIT 上,WhisperX 字詞邊界的平均誤差也有 110 ms,比 MFA 的 19.93 ms 差很多。
8. **Gemini 3.5 Transcribe 的限制**:開啟字詞時間戳「可能降低轉寫準確度」,而且不能和 custom_vocabulary 併用,所以 AI 術語的辨識會變差。
9. **manim-voiceover 的風險**:仍是 Alpha;兩個版本之間隔了約 21 個月;Gemini 整合是否支援 OpenRouter 未查證。
10. **響度標準被當成官方規範**:-14 LUFS 是慣例,不是 YouTube 官方數字;觀眾端的穩定音量還會再動態調整你的混音。
