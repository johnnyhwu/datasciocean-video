# DataSci Ocean YouTube 影片專案規劃(給你看的版本)

Nov 1, 2026 · @YHHW

## 30 秒版本

把 DataSci Ocean blog 的觀念卡,自動做成 3Blue1Brown 風格的 YouTube 講解影片:繁體中文為母片,長度 3 到 15 分鐘,目標每週 1 支。Claude Code 負責製作,你負責四個人審關卡和最後的發布。

- **唯一資料來源**:concept-wiki,以唯讀 submodule 接入。影片傳達的知識不超出觀念卡,唯一的例外是教科書等級的前置知識。
- **三個目標**:吸引點擊、好理解而且願意看完、帶得走一句話。忠實是硬性限制,不和三個目標取捨。
- **核心做法**:具體例子先於定義;畫面上每個動作都要有目的;旁白先行,動畫綁在旁白上。
- **聲音**:Gemini 3.8 Flash TTS 複製你自己的聲音,試聽後定案;Gemini 預設聲音是備案。
- **海外**:繁中母片,另附簡體字幕、英文自動配音、多語標題與說明。
- **最大風險**:不是 AI 揭露,也不是版權,而是影片之間看起來像模板量產,觸及 YouTube 的「通用或重複內容」政策。對策是反模板檢查,以及每支影片在視覺和結構上實質不同。
- **落地順序**:準備 → 工具與聲音實驗 → 第一支試片 → 存 2 到 3 支緩衝 → 每週發布。

## 1. 目標與定位

頻道定位是一句話:**用 3 到 15 分鐘的動畫,把一篇 AI 論文的核心機制講清楚,講給知道 LLM、但不讀論文的人聽。**

### 三個目標

觀眾要連過三關,影片才算成功。每一關都有對應的設計和檢查問題。

| 目標 | 對應的設計 | 檢查問題 |
| --- | --- | --- |
| 吸引點擊 | 承諾句、標題、縮圖、開場 | 這個承諾會讓目標觀眾想點進來嗎?字面為真嗎? |
| 好理解、願意看完 | 骨架、暖身例子、前置知識、動畫 | 聰明的外行跟得上嗎?哪一段最容易讓人離開? |
| 帶得走東西 | 一句話重點、結尾 | 這支影片的重點能用一句話說完嗎? |

長期目標還有**營利**,但依研究 E,第一年不當作 KPI(見第 7 節)。

### 定位決定

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| 主要目標排序 | 訂閱成長為主,導流 blog 為輔;影片可以提 blog,但不強調 | 觀眾在影片上看完、有收穫,就算成功 |
| 觀眾 | 聰明的外行:知道 LLM 和一些流行詞,不讀論文或技術部落格 | 既不用從零解釋每個詞,也不假設觀眾懂論文 |
| 風格 | 以 3Blue1Brown 為準;批判觀點只小部分帶過,以忠實呈現新知為主 | Two Minute Papers 只是長度上的參考 |
| 格式 | 橫式 16:9,3 到 15 分鐘 | 3B1B 式動畫原生適合橫式;直式要整套重做 |
| 直式短影片 | 未來當宣傳用的衍生品,現在不做 | 先把主力流程跑通 |
| 平台 | 主力影片只放 YouTube;直式短片未來放 Shorts 與 IG Reels | IG 以直式為主,橫式影片在 IG 上太小 |
| 頻道 | 沿用現有頻道,名稱維持 DataSci Ocean | 與 blog、podcast、IG 一致 |
| 語言 | 繁中為母片;從第一支起附簡體字幕、英文自動配音、多語標題與說明 | 依研究 D,台灣頻道超過 40% 的觀看時間來自海外 |

### 差異點

依研究 D,「繁體中文加 3B1B 式動畫加 AI 論文機制講解」這個組合目前沒有人做,看起來是沒人做,不是做了失敗。繁中市場現有的是長篇課堂錄影(李宏毅)和 AI 工具教學(泛科學院),「10 分鐘內、動畫、只講一個機制」這一格是空的。D 推論合理的訂閱天花板是數萬到十多萬,不是百萬。

## 2. 內容設計

一支影片講一個觀念,內容全部來自觀念卡,用「具體例子先於定義」的骨架展開,並經過逐句查核。

### 2.1 一支影片由哪些卡組成

- **系列卡**(同一篇文章的多張卡):合成一支影片。
- **獨立卡**:一張卡就是一支。內容不足 3 分鐘時標成 `waiting`,可以和其他相關的獨立卡合併,可以跨文章;由 Claude Code 提候選組合,你決定。
- **長度**:3 到 15 分鐘。超過 15 分鐘時預設拆成系列,依觀念邊界切,不依時間切;只選主軸卡做一支的做法也會列出來比較。切法由你決定。
- **跨文章合併的限制**:只能講各張卡上有的內容,不能自行加上卡上沒有的比較(例如「A 方法比 B 好」)。

### 2.2 選題標準

| 項目 | 角色 | 內容 |
| --- | --- | --- |
| 觀念類型 | 分類 | 機制型(流程、結構)或事實型(數據、比較)。兩種都做,類型決定呈現手法 |
| 前置知識成本 | 篩選 | 這張卡需要的前置知識,能不能在影片裡用合理的篇幅補完 |
| 內容量 | 門檻 | 至少 3 分鐘;不足就標 `waiting` |
| 證據 | 篩選 | 卡上的主張有足夠的證據支撐 |
| 暖身例子(機制型) | 篩選 | 必須有一個能承載核心機制的小例子;卡上的機制描述不夠細就標 `unsuitable` |
| 可演的東西(事實型) | 篩選 | 必須有具體案例或可逐項揭露的比較;沒有就標 `unsuitable` 或 `waiting` |

### 2.3 腳本骨架

依研究 A,3B1B 的核心是「具體先於抽象」:定義是推導的終點,不是起點。

**機制型卡(七段)**

1. Hook:具體問題加一個具體數字或畫面(約 5 到 10%)
2. 為什麼值得在乎:接回觀眾熟悉的詞(約 5%)
3. 暖身例子:用小而乾淨的例子承載核心機制(約 25 到 35%)
4. 讓觀眾注意到規律,再命名概念(約 20 到 25%)
5. 接回卡上的真實設定與證據(約 15 到 20%)
6. 限制(約 10% 以內,卡上沒有就略過)
7. 帶走什麼,輕提 blog

**事實型卡(六段)**:Hook → 疑問的背景 → 數據逐項揭露 → 解讀 → 限制 → 帶走什麼。

百分比是研究 A 從樣本影片推論出的比例,可以調整。骨架是預設順序,每支影片可以變動,但要說明變了什麼、為什麼。

### 2.4 承諾句與包裝(hook)

依研究 F,YouTube 官方把「開頭留存」定義為前 30 秒,並把它和「內容是否符合標題與縮圖的預期」直接連在一起;哪一種開場模式最好,則沒有可信研究。

1. 先寫**承諾句**:觀眾看完會知道的那一件事。它就是「一句話重點」。
2. Claude Code 產出 2 到 3 組**包裝**:每組含標題、縮圖文字、縮圖畫面描述、前 30 秒開場。各組用不同開場模式,講同一個承諾,並附一行理由說明觀眾為什麼會點、為什麼會看下去。
3. 開場模式:主力是反直覺問題、成果先展示、明確目標;輪替用想像情境、視覺謎題;不用互動挑戰、痛點承諾、標題快閃。
4. **前 30 秒內**出現第一個實質內容(一個問題的線索、關鍵畫面或數字)。這不是定義,定義仍在暖身例子之後。
5. 每組附「承諾在第幾秒兌現、用哪個畫面、對應卡上哪一句」。對不上就淘汰。
6. 包裝可以自由創作;事實一律回到卡上。不用「震驚」「顛覆」「竟然」;開場不以頻道介紹或長片頭開始。
7. 你在關卡 2 挑一組。

### 2.5 結尾

帶走什麼(回收承諾)→ 輕提 blog → 系列指引(只有系列影片才有)。不提 podcast,不口頭呼籲訂閱。

### 2.6 忠實度規則

**先自由寫、寫完才查核。** 寫腳本時只守「事實來自卡」;寫完後由獨立的查核員逐句標記、查來源,查不到的退回改寫。這樣規則不會讓腳本變得死板。

| 標記 | 是什麼 | 嚴格度 |
| --- | --- | --- |
| `card_claim` | 卡上的事實、數字、主張、實驗結果 | 最嚴:必須回到卡上原文,不能比卡更強;附來源類型(設計參數、實驗結果、官方宣稱、作者判斷) |
| `prerequisite` | 教科書等級的前置知識 | 不碰論文主張;和卡衝突以卡為準;比例暫定不超過三分之一 |
| `illustration` | 暖身例子、示意例子 | 每一步要能對回卡上的機制(附對照表);畫面標「示意」 |
| `framing` | hook、轉場、比喻、假設情境 | 放寬:只用程式掃描有沒有夾帶數字、比較詞、因果詞 |
| `fixed_line` | 你寫好的固定句 | Claude Code 只能填變數;數量縮到最少 |

其他規則:

- 一句一個標記,混合句要拆開;畫面上的字和數字同樣要查核。
- 禁止自己推算新數字(例如把卡上兩個數字相除)。
- **每個數字三項齊全**:量的是什麼、比較對象、限定條件;比例要寫出分母。
- 取整不能改變意思:31% 可以說「約三成」,不能說「超過三成」。
- **每個關鍵數字的限定條件,旁白至少完整說一次**,畫面再補充細節。這樣繁中、簡體、英文配音三種版本都忠實。
- 規則卡住好內容時,先改表達方式;仍然不行就回報給你決定。
- 遇到不屬於任何標記的內容,停下來問你。

**限制段**:只來自卡;最多 1 到 2 個;約佔 10% 以內;只放會改變觀眾對結論信任程度的限制;卡上沒有就整段略過。

### 2.7 系列與命名

- 系列影片採「獨立,但有建議順序」:每集開場獨立可懂;回顧前集最多 1 到 2 句,只重述卡上內容;只預告已經做好或已排定的下一集。
- 系列名稱以觀念命名,不用論文名;集數不放在標題開頭。系列名稱由 Claude Code 提候選,你決定,發布後不改。
- 每支影片在 repo 裡的資料要記錄來源卡 ID 清單,供查核員追溯。

## 3. 視覺與動畫

動畫要大膽有創意,但每個動作都要有目的;工具不定死,由實驗決定。

### 3.1 要學 3B1B 的什麼

依研究 A,3B1B 的原則是「每個畫面上的移動都要有可辨識的目的,而且和旁白講同一件事」。所以「豐富的動畫」指的是該動的地方都有動,不是動得多。

| 風格要素 | 處理 |
| --- | --- |
| 敘事:具體例子先於定義 | 照搬,已寫進骨架 |
| 動作紀律:每個動作對應旁白的一句話,同一時間只有一個焦點 | 照搬,寫成檢查規則 |
| 視覺語彙:同一概念全片同色、逐步揭露、重用同一張圖、可操作的分布 | 照搬 |
| 公式與配色參數 | 改造:中文字型另配,參數見 3.4、3.5 |
| 吉祥物角色 | 不做:那是 3B1B 的識別,也有授權疑慮 |

**創意規則**:每個場景先提 2 到 3 個不同的視覺構想(不同的比喻、構圖、動作語彙),附一句理由,再挑一個做。比喻只翻譯,不夾帶卡上沒有的事實。好不好看、好不好玩,由你判斷。

### 3.2 工具:不定死,由實驗決定

依研究 B,目前證據最多的是 **ManimCE**(Manim 的社群版):MIT 授權,營利無限制;最貼近 3B1B 風格;有 6 個公開的 AI agent 自動生成講解影片案例;只用 CPU 渲染。它是**起點**,不是決定。

- Claude Code 可以嘗試任何工具,包括 Remotion、HyperFrames,以及 WebGL/three.js(瀏覽器的 3D 繪圖,做空間感強的場景)。
- 最後用哪個工具,看第 8 節的工具比較實驗,由你決定。
- 不管用哪個工具,都要守硬性限制:授權允許營利;同樣輸入產出同樣影片;通過動作紀律與渲染後看圖檢查;繁中正確顯示;同一專案不混用 ManimGL 和 ManimCE。
- 3b1b/videos 的程式碼是 CC BY-NC-SA 授權,禁止商業使用,只能參考寫法,不能複製。

B 提醒 ManimCE 的三個弱點:中文換行要自己切;版面最常出錯(重疊、超出畫面);AI 可能寫出不存在的 API。前兩者靠輔助函式和格線定位解決,最後一個靠 skill 和專案規則。

### 3.3 版面

- 畫面分四區:安全邊界、主畫面區、條件標註區、字幕區。元素只能放進區域裡。
- 主畫面區用格線定位(起點 6×6,依 B 引用的 Code2Video 案例)。分區和格線由輔助函式強制,動畫程式只能指定格子,不能自己填座標。
- 最小字級用「占畫面高度的比例」表示;條件標註也要達到最小字級。數值在實驗中用手機實際看過再定。
- 畫面文字要少而短,多用數字、公式、符號、圖示。這同時照顧手機可讀性和英文配音觀眾(他們看不懂畫面上的中文)。

### 3.4 配色

- 背景純黑或接近純黑(A:3B1B 用純黑)。
- 同一概念全片同一顏色,公式和圖形中的同一個量同色。
- 每支影片的概念色 4 到 5 種(暫定),其他用中性色。
- 不只靠顏色傳達資訊,還要有形狀、標籤或位置的區別。
- 頻道固定少數「角色色」(強調、正確、錯誤、中性);概念色每支影片自己指定。
- 品牌色從你各專案共用的 logo 抽出,只用在片頭、縮圖和頻道識別,不當概念色。
- 程式檢查:文字對比度至少 4.5:1(網頁無障礙標準 WCAG AA,當起點)、同概念不跨色、概念色不超量。

### 3.5 字型

- 預設 Noto Sans TC(思源黑體)。依研究 H,它是 SIL OFL 1.1 授權,可用於營利影片。jf 粉圓、霞鶩文楷 TC、台北黑體也是 OFL,可以試作標題字型。
- 全片最多 2 種字型:中文字型加公式字型。
- 字重至少一般(Regular)。
- 字型檔放進 repo 並固定版本,附授權文字檔。微軟正黑體預設不用;華康、文鼎等商業字型禁用。
- 程式檢查:每個字都有收錄、顯示的是繁體字形。

### 3.6 事實型卡怎麼做得生動

事實型卡沒有流程可畫,用以下手法讓數據變成敘事。Claude Code 依卡上實際有的數據挑選,並寫下理由。

| 手法 | 卡上要有什麼 | 忠實限制 |
| --- | --- | --- |
| 先預測再揭曉(預設) | 可比較的數字 | 揭曉的數字必須是卡上的 |
| 具體案例當錨點(預設) | 一個具體案例 | 案例必須來自卡,不能自編 |
| 逐項揭露的圖表(預設) | 一組比較數據 | 縱軸從零開始;要有比較對象和分母 |
| 前後對照(預設) | 方法前、後的結果 | 兩側條件完全一致才能並排 |
| 拉動旋鈕(選單) | 多個設定下的結果 | 只畫卡上有的點,點之間不畫平滑曲線 |
| 拆解(選單) | 總數與各部分 | 各部分加總要等於總數 |
| 熱力圖(選單) | 多條件多指標的結果表 | 色階要有圖例 |
| 條件逐層加上去(選單) | 數字附帶條件 | 最低風險 |

純表格停在畫面上念數字,這種做法不用。

### 3.7 論文圖

- 觀念卡會附原始論文的圖。**影片一律重新製作,不放原圖。** 依研究 H,數據本身不受著作權保護,依數據重新製作的圖不需要許可;從原圖檔案修改則算改編。
- 重畫時重新設計版面、配色和風格,不逐筆描摹。
- 數字只用卡上有的,或圖上有標的。圖上沒標、只能從長條高度估讀的,只畫示意並標「示意」;需要精確數字就停下來問你。
- 查核員把重畫圖和原圖逐項比對(數值、順序、比較對象)。
- 不逐圖標示出處;出處放說明欄,內容是對應的 blog 文章連結。

## 4. 旁白、音樂、字幕

旁白用你自己的複製聲音,逐句生成,動畫跟著旁白走;字幕、音樂、響度都由程式檢查。

### 4.1 聲音

依研究 K,Gemini TTS 現在可以複製你的聲音,不必換供應商。

- **主力**:Gemini 3.8 Flash TTS 加你的複製聲音,走 Gemini API 直連、付費層。需要一段 10 到 30 秒的乾淨錄音,加一段本人唸的同意聲明。成本約 US$0.14 一支 10 分鐘旁白,2027 年起約加倍。
- **備案**:Gemini 預設聲音(現在 podcast 用的)。
- **定案方式**:實驗中盲聽比較你的複製聲音、Gemini 預設聲音、Azure 台灣華語聲音、BreezyVoice(聯發科開源,專為台灣華語設計)。
- **三個待測風險**:同意聲明只有簡體版,台灣口音唸能不能通過驗證(不行就改唸英文版);複製聲音可能不能透過 OpenRouter 呼叫(推論);沒有發音字典,多音字唸錯只能改寫文字繞過。

### 4.2 口語腳本

- 句子短,一句一個重點;台灣口語的繁體中文。
- 每句旁白存**兩份文字**:唸法稿給 TTS(「百分之三十一」),顯示稿給畫面和字幕(「31%」),以句子 ID 對應。
- 英文縮寫首次出現時附全名和一句話說明。
- 容易唸錯的英文詞建發音對照表。
- 語音辨識回聽:把音檔轉回文字,和唸法稿比對,抓唸錯、漏唸、多唸。可靠程度要在實驗中驗證。自不自然由你聽。
- 腳本參考你 podcast repo 的風格規則(開工時一次性抽出)。

### 4.3 旁白與動畫的對時

依研究 C,Gemini TTS 不回傳任何時間戳。所以採**旁白先行**:

1. 每句旁白單獨生成音檔,音檔長度就是那句的精確時間。
2. 語音辨識回聽,唸錯就重生成。
3. 只有「講到某個詞要觸發動畫」的地方,才做字詞級的強制對齊。沒有繁中的正式評測,實驗中人工抽查 50 句。
4. 依句子長度算出場景長度,動畫時間寫成「相對於某句或某個詞」,不寫絕對秒數。
5. 每個場景留一段可伸縮的停留時間。
6. 場景各自渲染,以內容雜湊快取:改一句旁白,只重做那句和它所在的場景。

3B1B 自己是先動畫後旁白;研究 A 和 C 都建議反過來,因為自動化需要可重現性。逐句生成可能讓句間語調斷掉,實驗中會和「整個場景一次生成」做比較。

### 4.4 字幕

- 主力影片用**軟字幕**(上傳 SRT 檔):不佔畫面,上傳後還能修改。
- 繁中字幕用顯示稿;**簡體字幕**用工具從繁中轉換,並做地區用語轉換。
- 斷行(研究 C 引用的 Netflix 繁中規範):每行最多 16 個全形字,每個字幕最多 2 行,每秒最多 9 個字;先在標點斷,不在數字和單位、英文單字、專有名詞中間斷。
- 中英之間是否加空格全片統一,開工時參考 podcast 和 blog 的慣例。
- 即使用軟字幕,畫面下方的字幕區仍保留,避免重要內容被 YouTube 的字幕擋住。

### 4.5 音樂與音效

- 片頭、片尾、段落轉換時有音樂;旁白時音樂降到很低或停掉。
- 來源以 YouTube 音訊庫為主(依研究 H,不會被 Content ID 認領,可營利)。標 CC 的曲目要在說明欄標示;Pixabay 備用並保留下載證明;AI 生成音樂預設不用。
- 由你挑一個小曲庫,Claude Code 只能從曲庫選。音樂檔不進 git,因為 YouTube 音訊庫條款禁止單獨散布音樂檔。
- 片頭固定一小段音樂當識別;段落中的音樂從曲庫輪替,避免每支聽起來一樣。
- 音效少量,每個音效都對應一個畫面事件。

### 4.6 響度

- 目標:整支平均 -14 LUFS(依人耳感受衡量的平均音量),最高點不超過 -1 dBTP(最高的瞬間音量)。研究 C 查證過,YouTube 官方沒有公布數值,這是業界慣例。
- 每句先做輕量的音量一致化;場景音訊保持未壓縮;全片串接混音後,只做一次兩段式正規化;最後轉成 48 kHz 再編碼。
- 程式檢查:響度在目標 ±1 內、峰值、取樣率、場景接縫沒有空白、頭尾沒有多餘靜音。

### 4.7 AI 揭露與政策

依研究 G 和 K 讀到的 YouTube 官方原文:

| 情況 | YouTube Studio「AI use」欄位 |
| --- | --- |
| 主力:你的複製聲音、程式動畫、AI 依你的 blog 寫腳本 | **No**:官方明列複製自己的聲音、非寫實動畫、AI 寫腳本與標題縮圖都不需揭露 |
| 備案:Gemini 預設聲音 | **建議 Yes**:官方沒有明確答案;選 Yes 只會在說明欄展開處出現標籤,官方說不影響推薦和營利 |

配套規則:

- 每支影片都明確作答,不留空。Claude Code 在上傳清單寫好建議答案和理由。
- 上傳前檢查影片檔有沒有殘留 C2PA 來源憑證(複製聲音帶有這種憑證,YouTube 可能據此自動加上無法移除的標籤)。
- 旁白不設虛構人設或專家身分。
- 頻道「關於」頁寫一段製作方式說明。

比揭露更大的風險是「通用或重複內容」政策,見第 5 節的反模板檢查。

## 5. 自動化流程

從觀念卡到成片是九個步驟、四個人審關卡;失敗 3 次就停下來回報,不自己硬做。

&#91;embedded content: 從觀念卡到成片 · 9 個步驟、4 個人審關卡\]

查核不通過時退回改寫,最多 3 輪;任一步驟失敗 3 次就停下來回報。

關卡 2 最重要:這是渲染前最後一次修正的機會。研究 A 說暖身例子的設計最需要人判斷;研究 B 引用的案例也發現,失敗多半出在「這段要讓觀眾理解什麼」沒想清楚。到成片才發現,動畫和旁白就要整批重做。

### 5.1 repo 結構

**唯一的依賴是 concept-wiki**(唯一的 submodule)。social-media 和 podcast repo 只在第一次開工時參考一次:抽出品牌色、hook 規則、命名慣例、腳本風格、TTS 設定,複製進新 repo 並註明來源與日期。之後那兩個 repo 修改,影片 repo 不會自動跟進。

| 目錄 | 內容 |
| --- | --- |
| `concept-wiki/` | submodule,唯讀,由程式擋住寫入 |
| `CLAUDE.md` | 跨步驟的原則,保持精簡 |
| `.claude/skills/`、`.claude/agents/` | 每個步驟一份 skill;查核員、視覺檢查員兩個 subagent |
| `rules/` | 資料性質的東西:發音對照表、固定句、從其他 repo 抽出的參考 |
| `research/` | 研究報告原文(A、B、C、E、F、G、H、K、L) |
| `assets/` | 字型與授權檔、曲庫授權紀錄、logo |
| `lib/` | 版面輔助函式、各項程式檢查 |
| `videos/<影片 ID>/` | 每支影片的規劃、腳本、查核紀錄、上傳清單、結構指紋 |
| `state/` | 每張卡與每支影片的狀態 |
| `experiments/` | 實驗紀錄 |

不進 git 的東西:API 金鑰(放環境變數)、音檔與渲染出來的影片(放本機)、曲庫的音樂檔、你的聲音錄音。即使 repo 不公開也照這個標準。

### 5.2 狀態、快取、失敗

- 每支影片有明確的狀態;每個狀態有完成條件,沒達到不往下走。遇到人審關卡就停住,你核准後才繼續,核准紀錄附日期。
- 每張卡的狀態:候選、`waiting`、`unsuitable`(附原因)、製作中、已做成影片;每筆附 concept-wiki 的 commit。卡在製作中途被修改,不自動跟進,通知你。
- 內容雜湊快取:內容沒變的音檔和場景不重做。
- 失敗容忍 3 次(查核改寫 3 輪、場景渲染 3 次),超過就停下來回報。不採用研究 B 案例的「自動換成投影片式備援畫面」,因為那會違反風格,也像模板。
- TTS 碰到每日上限不算失敗:暫停,隔天從同一句接著做。

### 5.3 分工

| 角色 | 負責 |
| --- | --- |
| 程式(`lib/`) | 能用規則判斷的檢查全部交給程式:字幕、響度、C2PA、字型缺字、對比度、色彩數量、元素超出分區、標記完整、數字是否在卡上、前置知識比例、影音長度、語音辨識錯誤率、快取、狀態、擋寫入 submodule、反模板的結構指紋比對 |
| 主流程(Claude Code) | 選題、規劃、寫腳本、寫動畫程式、組裝影片、在關卡交付 |
| 查核員(subagent) | 只看腳本和卡;逐句查來源、比對暖身例子、比對重畫圖與原圖 |
| 視覺檢查員(subagent) | 只看抽出的畫面和場景規格;檢查版面、動作紀律、配色 |
| 你 | 四個關卡、盲聽、好不好看 |

反模板檢查不設 subagent:每支影片完成時寫一份很小的「結構指紋」(開場模式、段落順序、視覺手法、背景音樂),由程式比對最近 5 支,相似度太高才交給主流程判斷。

### 5.4 token 與使用額度

你用的是 Claude Code 訂閱方案,所以「太貴」的意思是「太耗使用額度」,而額度由你所有 Claude Code 專案共用。

- 研究報告只當存檔,開工時一次提煉成精簡規則;細節放在 skill,執行到該步驟才載入。
- 先用程式檢查,通過了才送圖給視覺檢查員;每場景只抽 1 張低解析度畫面。
- 查核只重查改過的句子;數字先用程式比對字串。
- 動畫只改出錯的場景;錯誤訊息只留相關幾行。
- subagent 只回傳結構化的簡短判定。
- 狀態存在檔案裡,可以隨時開新對話接續,不帶著整段歷史。
- 規劃、例子、腳本用較強的模型;標記這類機械性工作用便宜的模型。

### 5.5 成本與時間

大部分成本要實測才知道。第一批 2 到 3 支影片做完後,算出每支的額度消耗、TTS 金額、渲染時間、你的審查時間,再找最貴的步驟優先優化。

| 項目 | 目前所知 |
| --- | --- |
| TTS(另外用 API 計費) | 約 US$0.14 一支 10 分鐘(研究 K,付費層),2027 年起約加倍 |
| 渲染 | 研究 B 推估 5 分鐘影片約 20 到 38 分鐘,只用 CPU;要實測 |
| 3 到 15 分鐘的字數門檻 | 由 podcast 實際音檔算出每分鐘字數再換算 |
| Claude Code 額度 | 每步記錄;拿不到用量就記錄重試次數和送檢圖片張數 |

每個關卡你只看一份「審查包」,裡面只放需要你判斷的東西;程式已經通過的檢查,只用一行帶過。

### 6.1 四個關卡的審查包

| 關卡 | 審查包內容 | 你要做的事 |
| --- | --- | --- |
| 1 選題 | 候選清單:用了哪幾張卡、機制型或事實型、預估長度、一句話重點、暖身例子的初步想法;`waiting`、`unsuitable` 的原因 | 選題,決定合併或拆集 |

### 6.2 回饋與回顧

- **每個關卡**:你直接用口語給回饋,Claude Code 依回饋修改這支影片。
- **每支影片發布後**:你請 Claude Code 回顧這次的執行過程,找出可以改進、要記住、要避免的地方,再修改 `CLAUDE.md` 和相關的 skill。
- 修改先列給你看,你同意才寫入。git 的提交紀錄就是規則的演變紀錄。
- 回顧不能悄悄放寬硬性限制(忠實、授權);想放寬一定要明確問你。
- 細節規則寫進對應的 skill,`CLAUDE.md` 只放跨步驟的原則。
- 每週都要做一次回顧,所以回顧要簡短,只改確實有需要的地方。

## 7. 發布與成長

目標每週 1 支、固定排程;營利是長期目標,第一年先追訂閱與觀看時數的累積。

### 7.1 頻道改版(第一支發布前完成,只做一次)

| 項目 | 做法 |
| --- | --- |
| 名稱 | 維持 DataSci Ocean |
| 簡介 | 從「Python 初學者教學」改成新定位;Claude Code 提 2 到 3 版,你選 |
| 「關於」頁 | 加一段製作方式說明,例如「腳本改寫自本人 blog,動畫以程式繪製,內容經本人審閱」 |
| 舊的 Python 影片(約 15 支) | 整理成獨立播放清單,不刪除;頻道首頁把新影片放最前面 |
| 帳號 | 完成驗證(系列播放清單需要),開通進階功能(A/B 測試需要),確認自動配音的開通條件 |
| 頭像與橫幅 | 依 logo 抽出的品牌色製作 |
| 頻道頁連結區 | blog、podcast、IG、Threads |

依研究 E:舊訂閱者大多不會點新影片,這是正常的(YouTube 官方說訂閱者點擊率在 10% 以下是常態);前幾支的數據會像新頻道,至少做滿 10 支再判斷方向。

### 7.2 標題、縮圖與 A/B 測試

- 標題 30 個中文字以內,核心承諾放在前 20 字(研究 F 的推論,YouTube 未公布手機截斷字數);前半放搜尋詞,後半放問題或反差;英文術語保留原文。
- 縮圖畫面直接取自影片動畫的高解析度畫面;縮圖文字 2 到 6 字,補充標題不重複;解析度至少 1280×720;不用寫實 AI 人像或影片中沒出現的 logo。
- **每支影片都做 A/B 測試**:你選定開場後,Claude Code 依同一個承諾準備 2 到 3 組標題加縮圖。YouTube 依觀看時間分配比例判定勝負,不看點擊率;測試中修改會自動停止。新頻道曝光少,多半會「沒有定論」,所以每次都記錄開場模式和標題寫法,累積 10 支以上再看趨勢。

### 7.3 說明欄、章節、片尾畫面

- 說明欄(Claude Code 起草):開頭用承諾句改寫的摘要;對應的 blog 文章連結;論文資訊卡上或文章裡有才列;系列其他集的連結;章節;CC 音樂標示;用備案聲音時加一行 AI 說明。不放 podcast。
- 章節從場景資料自動算出。YouTube 章節規則(首個 0:00、至少 3 段、每段至少 10 秒)是記憶,開工時確認。
- 片尾畫面放系列或下一支影片,加上訂閱按鈕;最後一個場景要留出乾淨的時間和空間。
- IG、Threads 的導流屬於 social-media repo,影片 repo 不碰。

### 7.4 多語

| 項目 | 做法 |
| --- | --- |
| 簡體字幕 | 從繁中字幕轉換,含地區用語轉換 |
| 英文 | YouTube 自動配音(研究 D 確認支援繁中配英文);還不能用時,改上傳英文翻譯字幕 |
| 標題與說明 | 同時起草英文、簡體版本,在關卡 4 一起定稿 |
| 翻譯的忠實 | 只翻譯,不多加說法或誇大 |

### 7.5 發布節奏與營利

- **目標每週 1 支,固定排程。** 研究 E 引用的資料:YouTube 官方說不懲罰低頻上傳;第三方大樣本顯示上傳越頻繁成長越快、固定排程較好,但都只是相關性。
- 正式進入每週節奏前,先存 2 到 3 支緩衝,避免斷更。
- 品質關卡不為趕進度放寬;沒過就拿緩衝頂上。
- 開工時盤點 concept-wiki 的題材庫存;撐不了幾週就先告訴你。
- 以常青的觀念與機制為主,不寫成「最新論文快報」。
- 營利:依研究 E 與 G,2027 年 2 月 1 日起新申請門檻為 1,000 訂閱加 365 天內 8,000 小時有效觀看(研究 L 在 YouTube 說明中心找到官方原文確認;現行門檻是 4,000 小時,新制另有 90 天 2,000 萬次 Shorts 觀看的路線)。新頻道在新制前達標的機率很低,所以直接以新門檻為目標。
- 規模感(全部是假設):影片平均 10 分鐘、觀眾平均看三成,每次觀看約 3 分鐘,8,000 小時約需一年 16 萬次觀看。
- 業配、頻道會員等其他營利方式這次沒有研究。

### 7.6 成效追蹤

| 指標 | 是什麼 | 衡量哪一關 |

| CTR(曝光點擊率) | 看到縮圖的人有多少比例點進來 | 被點進來 |
| 開頭留存 | 看完前 30 秒仍在看的比例 | 包裝的承諾和內容對不對得上 |
| AVD(平均觀看時長)、平均觀看百分比 | 每次觀看平均看了多久、看了幾成 | 被看完 |
| 訂閱轉換 | 新增訂閱除以觀看數(要自己算) | 願意長期關注 |
| 流量來源 | 搜尋、首頁、相關影片、外部 | 觀眾從哪裡來 |
| 營利進度 | 訂閱數、365 天有效觀看時數 | 長期目標 |

- 判斷影片好壞看 engaged views 和留存,不看表面觀看數(YouTube 2026 年 8 月改了觀看數的算法)。
- 每支影片在發布後第 7 天、第 28 天各記一次。第一天的數字不當真。
- 數據和結構指紋放在一起;每 10 支寫一份簡短報告。樣本小、主題熱門度會蓋過其他因素,所以當線索,不當結論。
- 數據取得方式見 7.7。

### 7.7 成效數據自動化(依研究 L)

用自寫的 Python 腳本呼叫 YouTube 三支官方 API,由作業系統每天排程執行,結果寫進 repo;Claude Code 只負責每 10 支影片做一次分析。A/B 測試結果和營利進度每月在 YouTube Studio 手動記一次。

**為什麼不用 MCP 當主幹**:Google 沒有官方的 YouTube MCP server。社群版本都很新、使用者很少,有的帶上傳或刪除等寫入權限,託管型還要把授權交給第三方。可以選擇另外包一個極小的唯讀本地 MCP,讓 Claude Code 在分析對話中臨時查詢;每日抓取仍交給腳本,因為固定的腳本比讓 LLM 每次自己組查詢更穩定。

| 指標 | 從哪裡取得 |
| --- | --- |
| 曝光次數、CTR | YouTube Reporting API 的 reach 報表(2026 年 1 月才上線) |
| 留存曲線、開頭留存 | YouTube Analytics API;一次只能查一支影片,第 30 秒的值要自己從曲線換算 |
| 平均觀看時長與百分比、訂閱增減、流量來源、engaged views | YouTube Analytics API |
| A/B 測試結果 | 沒有任何 API,每月手動記錄 |
| 訂閱總數、有效觀看時數 | API 只能近似(訂閱數會被捨去到 3 位有效數字;觀看分鐘數和營利用的「有效觀看時數」口徑不同),每月手動看 Studio「營利」頁 |

**要注意的地方**

- **第一支影片發布前就要建好 Reporting API 的報表 job。** 曝光與 CTR 只從建立 job 起算,最多回補前 30 天,錯過就只能去 Studio 看。
- **OAuth 設定**:個人自用不需要送 Google 審核,但要把同意畫面的狀態改成 In production(不送審)並重新授權。停在 Testing 狀態的話,授權 7 天就過期。
- 只給兩個唯讀權限範圍(`yt-analytics.readonly`、`youtube.readonly`),API 層級就無法上傳或修改。憑證放在 repo 外。
- **數據延遲 48 到 72 小時**:「第 7 天」的快照在發布後第 10 天抓,「第 28 天」的快照在第 31 天抓。日期一律以美國太平洋時間計算。
- 排程用作業系統的 cron 或 launchd,不用 Claude Code 的雲端排程:雲端排程讀不到本機的憑證檔。電腦常關機的話,改放在常開的機器上。
- Reporting API 的報表 60 天後刪除,所以每天下載並保存原始 CSV。
- 單支影片的新增訂閱只算從觀看頁按下的訂閱,會低估影片的貢獻;拿來比較影片之間沒問題。
- 觀看數在 2026 年 8 月 24 日改了算法,跨期比較一律用 engaged views。

## 8. 落地計畫

五個階段依序進行;前兩個階段不發布任何東西。

### 8.1 五個階段

1. **準備**:向你索取素材;探索 concept-wiki 並盤點題材庫存;一次性參考 social-media 和 podcast repo;把研究報告提煉成規則;帳號驗證、開通進階功能、確認自動配音條件。
2. **實驗**:
   1. 工具比較實驗(視覺):Claude Code 挑 2 到 3 個工具,做同一支 30 秒測試片(題材:Attention 機制,只測試、不發布),three.js 為選做項目。決定工具,並校準格線、字級、字重、概念色上限、對比度。
   2. 旁白與對時實驗:在同一支測試片加上旁白。驗證聲音複製能否開通、盲聽選聲音、逐句還是整場景生成、語音辨識回聽是否可靠、字詞對齊準確度(抽 50 句)、影音長度差在 0.3 秒內、旁白時的音樂音量、響度、字幕、C2PA。盲聽時由 Claude Code 隨機改檔名,你評分後才揭曉。
3. **第一支試片**:用一張真實的觀念卡,完整走完九個步驟和四個關卡。頻道改版在第一支發布前完成。
4. **存緩衝**:累積到 2 到 3 支;每支發布後照常回顧。第一支試片也算進緩衝,不急著發布。
5. **每週發布**:進入每週 1 支;成效追蹤開始。

每個實驗都限定時間和範圍,結果寫進實驗紀錄,最後由 Claude Code 寫成比較報告,你決定。

### 8.2 第一支試片

**選題條件**:機制型卡;有清楚的小例子;前置知識少;長度約 5 到 8 分鐘;不需要拆集。緩衝的第二支選事實型卡,讓兩條路徑都在每週發布前走過一次。

| 類別 | 成功標準 |
| --- | --- |
| 流程 | 九個步驟都跑完;失敗時有停下來回報;中斷後能從原處接續 |
| 忠實 | 關卡 3 沒發現事實錯誤,或發現的都是查核員已標記的 |
| 品質 | 你用手機看完,判斷看得懂、想看完、能用一句話說出帶走了什麼 |
| 外部觀眾 | 一位知道 LLM 但不讀論文的人看完,能用一句話說出學到什麼 |
| 效率 | 記錄額度消耗、渲染時間、你在四個關卡花的時間 |

觀看數、點擊率、訂閱數不列為試片的成功標準;研究 E 說至少要 10 支才看得出方向。

**試片沒過**:依問題出在哪裡,回到對應的規則調整(例如例子不行就回內容設計與視覺),再重做這一支,不急著進入緩衝階段。

**索引**

### Q1. 「聰明的外行不看論文也能懂」是什麼意思?

實際要檢查的是:**這張卡需要的前置知識,能不能在影片裡用合理的篇幅補完?** 有些卡的前置知識只要一兩句(例如「LLM 可以當評審」),有些本身就是一座山(例如講 KV Cache 分頁,得先講注意力機制和 GPU 記憶體)。這是成本檢查,不是硬性排除:補完後仍在 3 到 15 分鐘內就能做;前置知識多到補完就超時,才標成 `unsuitable`。

### Q2. 「先自由寫、寫完才查核」怎麼運作?

類比是雜誌的記者和事實查核員:記者自由寫稿,只守「事實要有根據」;寫完後由另一個人逐句標類型、查出處,查不到的退回。實作上是兩個獨立的 Claude Code subagent,查核員只讀稿子和卡。

例子(示範卡:「方法 X 在基準測試 Y 上讓費用下降 31%,比較對象是一律使用大模型」):

| 句子 | 標記 | 結果 |
| --- | --- | --- |
| 「為什麼讓小模型先看一遍,反而能省錢?」 | framing | 通過:沒有數字、不是斷言 |
| 「LLM 處理的每個字叫 token,費用依 token 計算。」 | prerequisite | 通過:教科書等級,計入比例 |
| 「想像有 4 份作業,小模型先批改。」 | illustration | 通過:畫面標「示意」 |
| 「在基準測試 Y 上,方法 X 讓費用下降 31%。」 | card\_claim | 退回:缺比較對象 |
| 「所以方法 X 一定比其他方法更省錢。」 | card\_claim | 退回:卡上沒有這個主張 |

### Q3. 五種標記夠用嗎?

最初只有三種(`card_claim`、`prerequisite`、`framing`),檢查後發現放不下兩類內容,因此新增 `illustration`(示意例子,3B1B 式動畫常用的自編小例子)和 `fixed_line`(每支重複的固定句)。另外補了四條規則:畫面上的字也要查核、混合句要拆開、禁止自行推算新數字、`card_claim` 要標來源類型。仍不能保證完全夠用,所以遇到不屬於任何標記的內容,一律停下來問人,讓缺口浮現,而不是被悄悄歸類。

### Q4. 標記會不會讓腳本變死板?

會,如果標記放在寫作的當下。所以規則是:寫的時候只守「事實來自卡」,其他完全自由;寫完才由另一個步驟標記和查核。嚴格度也分級:只有含事實的句子(數字、比較、因果、論文主張)要逐句回到卡上,包裝、轉場、比喻只用程式掃描有沒有夾帶事實。規則卡住好內容時,先換一種說法;仍然不行就回報給人決定。

### Q5. hook 一定要來自觀念卡嗎?

不用。知識不能超出卡,但 hook 是包裝:提問方式、切入角度、假設情境、比喻、開場畫面都可以自由創作。界線在事實:hook 裡的事實和數字一律要回到卡上;假設情境裡不能出現看起來像真實資料的數字(例如自編的「每天上萬次」)。hook 提出的問題,影片後面一定要兌現。

### Q6. WebGL 和 three.js 是什麼?能用嗎?

WebGL 是瀏覽器內建的功能,讓網頁程式直接呼叫顯示卡畫圖;three.js 是建在它上面的 JavaScript 工具箱,處理 3D 物件、鏡頭和燈光。做影片時,程式在每個時間點把場景擺好、截一格畫面,串起來就是影片。研究 B 沒有查這塊,所以它是工具實驗的選做項目。要測的風險:同樣輸入能否產出同樣畫面(動畫要由影格驅動,不能用即時時鐘)、沒有顯示卡時的渲染速度、繁中文字、以及特效會不會喧賓奪主。建議只用在需要空間感的概念上。

### Q7. Gemini TTS 能複製自己的聲音嗎?

可以。依研究 K 讀到的官方文件,2026 年 9 月推出的 Gemini 3.8 Flash TTS 有聲音複製功能,透過 Gemini API 自助開通,需要 10 到 30 秒的乾淨錄音和一段本人唸的同意聲明。限制是同意聲明的中文版只有簡體、沒有發音字典,而且透過 OpenRouter 呼叫可能不支援(推論)。依 YouTube 官方說明,用自己的複製聲音做旁白不需要 AI 揭露。

### Q8. 論文圖全部重新製作,還需要逐圖標示出處嗎?

不需要。依研究 H,數據本身是事實,不受著作權保護,依數據重新製作的圖不需要許可;標出處是學術慣例,不是法律要求,台灣智慧財產局也說標了出處不代表合法。所以畫面上不逐圖標示,出處放在說明欄,內容是對應的 blog 文章連結。唯一保留的標示是「示意」,用在只能從圖上估讀、不標精確數字的重畫圖,避免觀眾把估計值當成論文結果。

### Q9. social-media repo 需要當 submodule 嗎?

不需要。影片專案只依賴 concept-wiki。social-media 和 podcast repo 只在第一次開工時參考一次,把要用的東西(品牌色、hook 規則、命名慣例、腳本風格、TTS 設定)複製進新 repo 並註明來源和日期。代價是之後修改那兩個 repo 的規則,影片 repo 不會自動跟進;換來的是簡單的依賴關係。

### Q10. 一個月發幾支比較好?

目標每週 1 支。研究 E 引用的資料:YouTube 官方說不懲罰低頻上傳;第三方資料顯示教育與科技類頻道以每月 2 到 5 支表現最好、固定排程比隨機好、多次長時間停更較差,但都只是相關性,而且樣本是已有規模的頻道。每週 1 支的三個限制和你的時間無關:題材庫存、Claude Code 額度、影片之間變得太像的風險。所以正式開始前先存 2 到 3 支緩衝,品質關卡不為進度放寬,並在開工時盤點題材庫存。

### Q11. Claude Code 怎麼省 token?

訂閱方案下,token 消耗的是所有專案共用的使用額度。最耗的地方和對策:讀太多背景資料(研究報告提煉成精簡規則,skill 用到才載入);看圖(先程式檢查,每場景只送 1 張低解析度畫面);查核每輪重查整份腳本(只查改過的句子,數字先用程式比對);動畫反覆修改(只改出錯的場景);一個對話做太多事(狀態存檔,隨時開新對話接續);全部用最強的模型(機械性工作改用便宜的模型)。最大的省法是關卡 2:在渲染前把錯誤擋下,避免整批重做。
