# DataSci Ocean YouTube 影片專案:Claude Code 執行規格

Nov 1, 2026 · @YHHW

## 0. 任務與目標

你的任務:把 concept-wiki 的觀念卡,製作成 3Blue1Brown 風格的繁體中文 YouTube 講解影片,橫式 16:9、長度 3 到 15 分鐘,目標每週 1 支。使用者負責四個人審關卡與發布,不負責製作。

**頻道定位**:用 3 到 15 分鐘的動畫,把一篇 AI 論文的核心機制講清楚。觀眾是「聰明的外行」:知道 LLM 和一些流行詞,不讀論文。

**三個目標**(每支影片都用這三個問題自我檢查):

1. 吸引點擊:這個承諾會讓目標觀眾想點進來嗎?字面為真嗎?
2. 好理解、願意看完:聰明的外行跟得上嗎?哪一段最容易讓人離開?
3. 帶得走東西:這支影片的重點能用一句話說完嗎?

**規則分兩類**:

- **硬性限制**(第 2 節):不可違反,也不可在回顧時自行放寬。想放寬必須明確問使用者。
- **其他規則**:是目前的最佳做法,可以依實驗結果與使用者回饋調整。標示「暫定」的數值,都要在實驗中校準。

忠實是硬性限制,不和三個目標取捨:在不違反忠實的範圍內,把三個目標做到最好。

**不確定就停下來問**:遇到本文件沒有涵蓋的情況、規則彼此衝突、或某條規則明顯讓內容變差,停下來回報使用者,不自行決定。

## 1. 開工第一步

依序完成以下步驟,全部完成前不要開始製作影片。

1. **列出要向使用者索取的素材**,一次問完:
   - 各專案共用的 logo(用來抽取品牌色)
   - social-media repo 與 podcast repo 的存取權(只做一次性參考)
   - 使用者從 YouTube 音訊庫挑的小曲庫,以及每首的授權類型
   - 10 到 30 秒的乾淨語音錄音與同意聲明(用於 Gemini 聲音複製)
   - Gemini API 付費層金鑰(放環境變數)
   - 固定句(片頭識別句、blog 提示、系列指引)
   - `research/` 目錄中的研究報告原文
2. **探索 concept-wiki**(唯讀):觀念卡的格式、系列卡與獨立卡怎麼區分、卡的 ID 格式、圖片放在哪裡與怎麼命名、是否附圖號與說明、卡與 blog 文章之間有沒有連結欄位。把結論寫成一份簡短的格式說明放進 `rules/`。
3. **盤點題材庫存**:分類所有卡(機制型或事實型),依第 5 節標準初判,估算夠做幾支影片、在每週 1 支的節奏下撐得了幾週。撐不了幾週就告訴使用者。
4. **一次性參考兩個 repo**,把需要的東西複製進本 repo,每份開頭註明來源 repo 與複製日期:
   - social-media:品牌色、IG 封面的 hook 規則、命名與目錄慣例
   - podcast:腳本風格規則、TTS 設定與呼叫方式、發音處理方式、中英之間是否加空格的慣例
   - 之後不再依賴這兩個 repo。
5. **校準語速**:用 podcast 的實際音檔算出每分鐘唸幾個字,換算成 3 分鐘與 15 分鐘的字數門檻,寫進 `rules/`。
6. **提煉研究報告**:把 `research/` 的報告提煉成精簡的規則檔。報告本身只當存檔,平常不載入。
7. **確認外部規則的現況**(研究資料的時間是 2026 年 10 月,可能已變):
   - YouTube:章節規則、片尾畫面的時間與元素限制、A/B 測試與進階功能的開通條件、自動配音的開通條件與支援語言
   - Gemini TTS:聲音複製的 API、地區限制、能否經由 OpenRouter 呼叫、計費
   - 用到的動畫工具與字型的版本與授權
8. **回報**:完成第 9.1 節的成效數據初始化(必須在第一支影片發布前),再把以上結果整理成一份開工報告交給使用者,然後進入第 11 節的實驗。

## 2. 硬性限制

以下任何一條都不可違反;回顧時也不可自行放寬。

| 類別 | 限制 |
| --- | --- |
| 資料來源 | concept-wiki 是唯一資料來源,唯讀;用程式擋住任何寫入 submodule 的動作 |
| 知識範圍 | 影片傳達的知識不超出觀念卡。唯一例外是教科書等級的前置知識(第 5.6 節) |
| 忠實 | 不得加入卡上沒有的事實、數字、比較、因果;不得把說法說得比卡更強;不得自行推算新數字;限定條件不得刪除 |
| 翻譯 | 英文、簡體的標題、說明、字幕只能翻譯,不得多加說法或誇大 |
| 論文圖 | 一律重新製作,不放原圖,不逐筆描摹原圖的創意設計 |
| 授權 | 只用允許營利使用的工具、字型、音樂;不複製或改作 3b1b/videos 的程式碼與素材(CC BY-NC-SA,禁止商業使用) |
| 不進 git | API 金鑰與 OAuth 憑證、音檔與渲染出的影片、曲庫的音樂檔、使用者的聲音錄音。不論 repo 是否公開都照此處理 |
| 人審關卡 | 四個關卡都必須等使用者核准才繼續 |
| 失敗 | 同一項失敗 3 次(查核改寫 3 輪、場景渲染 3 次)就停下來回報;不自動換成投影片式的備援畫面 |
| 揭露 | 每支影片的「AI use」欄位都要有明確建議答案;上傳前檢查 C2PA |
| 人設 | 旁白不設虛構的人名、頭像或專家身分 |
| 外部依賴 | 不依賴 social-media 與 podcast repo(只在開工時參考一次) |

## 3. repo 結構

以下是起點;開工時參考 social-media repo 的目錄與命名慣例後調整。

| 目錄 | 內容 |
| --- | --- |

**版本與追溯**

- 每支影片記錄當時 concept-wiki submodule 的 commit,以及來源卡 ID 清單。
- 影片製作中途卡被修改:不自動跟進,維持原版本並通知使用者。
- git 只放文字類產物;音檔、渲染影片、音樂檔、聲音錄音放本機輸出目錄並加入 `.gitignore`。

## 4. 流程

九個步驟、四個人審關卡。每一步達到完成條件才能往下走。

| # | 步驟 | 輸入 | 輸出 | 完成條件 | 之後 |
| --- | --- | --- | --- | --- | --- |
| 1 | 選題 | concept-wiki、`state/` | 候選清單:來源卡、類型、預估長度、一句話重點、暖身例子初步想法;`waiting`、`unsuitable` 與原因 | 每個候選都通過第 5.1 節標準 | 關卡 1 |
| 2 | 規劃 | 選定的卡 | 承諾句、段落與時長、暖身例子與對照表、每場景 2 到 3 個視覺構想(推薦的那個附草圖)、2 到 3 組包裝 | 包裝通過第 5.3 節的自我檢查 | 關卡 2 |
| 3 | 寫腳本 | 規劃、卡 | 每句旁白的唸法稿與顯示稿,含句子 ID | 長度落在 3 到 15 分鐘的字數範圍 | — |
| 4 | 查核 | 腳本、卡 | 每句的標記、來源、判定;暖身例子對照結果 | 所有事實句都能回到卡上 | 不通過退回第 3 步,最多 3 輪 |
| 5 | 旁白 | 唸法稿 | 逐句音檔、時長、回聽結果、需要時的字詞時間戳 | 回聽字錯誤率低於門檻 | — |
| 6 | 動畫 | 規劃、腳本、時長 | 逐場景程式與渲染結果 | 通過版面、配色、動作紀律檢查與視覺檢查員 | — |
| 7 | 合成 | 場景影片、音檔、曲庫 | 成片、字幕檔 | 響度、長度、字幕檢查通過 | — |
| 8 | 成片自檢 | 成片 | 檢查結果、結構指紋、審查包 | 第 4.2 節所有程式檢查通過 | 關卡 3 |
| 9 | 發布準備 | 成片、承諾句 | 標題與縮圖(A/B 用)、多語標題與說明、章節、上傳清單 | 第 8 節規則通過 | 關卡 4 |

### 4.1 人審關卡與審查包

每個關卡交給使用者一份審查包,只放需要他判斷的東西;程式通過的檢查只用一行摘要。

| 關卡 | 審查包 | 使用者的決定 |
| --- | --- | --- |
| 1 選題 | 第 1 步的候選清單 | 選題、合併或拆集 |
| 2 規劃 | 第 2 步的產出 | 挑一組包裝;確認例子與視覺構想。選了沒附草圖的構想,渲染前補一張給他確認 |
| 3 成片 | 成片;被程式標記的項目(疑似夾帶事實的包裝句、示意例子、只畫示意的圖、前置知識段);和規劃不同之處;結構相似度;這次新增或修改的規則 | 用手機看完並回饋 |
| 4 發布 | 第 9 步的產出、C2PA 檢查結果、AI use 建議答案與理由 | 定稿並自行發布 |

使用者在關卡中的回饋,直接用來修改這支影片。核准紀錄寫進 `videos/<影片 ID>/`,附日期。

### 4.2 程式檢查清單

以下全部由 `lib/` 的程式執行,不交給 LLM:

- 字幕:每行字數、每秒字數、不可斷處、與顯示稿逐字一致
- 音訊:響度、峰值、取樣率、場景接縫無空白、頭尾無多餘靜音
- 影音長度差在 0.3 秒內
- C2PA 殘留
- 字型:缺字、繁體字形
- 配色:文字對比度、同概念同色、概念色數量
- 版面:元素是否重疊、超出分區、壓到字幕區
- 標記:每句都有標記;`card_claim` 有來源;數字能在卡上找到;前置知識比例;`framing` 句是否夾帶數字、比較詞、因果詞
- 語音辨識回聽的字錯誤率
- 結構指紋與最近 5 支的相似度
- submodule 寫入保護、內容雜湊快取、狀態轉換

### 4.3 狀態、快取、失敗

- 影片狀態:選題 → 規劃(等關卡 1、2)→ 腳本 → 查核 → 旁白 → 動畫 → 合成 → 成片(等關卡 3)→ 發布準備(等關卡 4)→ 已發布。
- 卡的狀態:候選、`waiting`、`unsuitable`(附原因)、製作中、已做成影片;每筆附 concept-wiki commit。
- 流程中斷後,從目前狀態接續,不從頭做。
- 音檔與場景依內容雜湊快取;內容沒變就不重做。關卡回饋後只重做受影響的步驟與場景。
- 失敗 3 次(查核 3 輪、渲染 3 次)停下來回報。
- TTS 錯誤:間隔拉長後重試。TTS 每日上限:暫停、記錄進度,重置後從同一句接續。

### 4.4 分工

- **主流程**:選題、規劃、寫腳本、寫動畫程式、組裝影片、交付審查包。
- **查核員**(subagent):只讀腳本與卡。逐句標記與查來源、比對暖身例子、比對重畫圖與原圖。只回傳結構化判定(通過或不通過、哪一句、原因)。
- **視覺檢查員**(subagent):只看抽出的畫面與場景規格。檢查版面、動作紀律、配色。只回傳結構化判定。
- **反模板檢查**:不設 subagent。每支影片寫一份結構指紋(開場模式、段落順序、使用的視覺手法、背景音樂曲目),由程式比對最近 5 支;相似度過高才交給主流程判斷是否調整。

## 5. 內容規則

### 5.1 選題與組成

**組成**

- 系列卡(同一篇文章的多張卡)合成一支。
- 獨立卡一張一支;不足 3 分鐘標 `waiting`,可和其他相關獨立卡合併(可跨文章),提候選組合給使用者決定。
- 跨文章合併時,只講各卡上有的內容,不加卡上沒有的比較。
- 超過 15 分鐘:預設依觀念邊界拆成系列,同時列出「只選主軸卡做一支」的方案,由使用者決定。拆出的每支都要 3 到 15 分鐘、有自己的一句話重點、開場獨立可懂。

**選題標準**

| 項目 | 規則 |
| --- | --- |
| 類型 | 分類為機制型或事實型,兩者都做 |
| 前置知識成本 | 前置知識能否在影片內合理補完;補完會超過 15 分鐘就標 `unsuitable` |
| 內容量 | 至少 3 分鐘(用 `rules/` 的語速門檻換算),不足標 `waiting` |
| 證據 | 卡上的主張要有足夠證據支撐 |
| 機制型 | 必須有能承載核心機制的小例子;卡上的機制描述不夠細就標 `unsuitable` |
| 事實型 | 必須有具體案例或可逐項揭露的比較;沒有就標 `unsuitable` 或 `waiting` |

### 5.2 骨架

原則:具體例子先於定義;定義是推導的終點。

**機制型(七段,百分比為暫定)**

1. Hook:具體問題加一個具體數字或畫面(5–10%)
2. 為什麼值得在乎:接回觀眾熟悉的詞(約 5%)
3. 暖身例子:小而乾淨的例子承載核心機制(25–35%)
4. 讓觀眾注意到規律,再命名概念(20–25%)
5. 接回卡上的真實設定與證據(15–20%)
6. 限制(10% 以內,可略過)
7. 帶走什麼,輕提 blog

**事實型(六段)**:Hook → 疑問的背景 → 數據逐項揭露 → 解讀 → 限制 → 帶走什麼。

骨架是預設;可以變動,但在審查包說明變了什麼、為什麼。前置知識在用到時才講,不集中放在開頭。

### 5.3 承諾句與包裝

1. 先寫承諾句(≤30 字):觀眾看完會知道的那一件事。它也是這支影片的「一句話重點」。
2. 產出 2 到 3 組包裝,每組含:標題、縮圖文字(2–6 字)、縮圖畫面描述(必須是影片中真的會出現的畫面)、前 30 秒開場、兌現位置(第幾秒、哪個畫面、對應卡上哪一句)、一行理由(觀眾為什麼會點、為什麼會看下去)。
3. 各組用不同的開場模式,講同一個承諾。主力:反直覺問題、成果先展示、明確目標;輪替:想像情境、視覺謎題;不用:互動挑戰、痛點承諾、標題快閃。
4. 前 30 秒內出現第一個實質內容(問題的線索、關鍵畫面或數字);不是定義。
5. 包裝可以自由創作;包裝中的事實與數字必須回到卡上。假設情境中不得出現看起來像真實資料的數字。
6. 禁用:「震驚」「顛覆」「竟然」等誇大字眼;縮圖用影片中沒有的畫面;以頻道介紹、贊助、長片頭開場;「記得訂閱」。
7. 每組逐項自我檢查:字面是否為真;承諾在第幾秒兌現;只看標題與縮圖的人會不會誤會主題;第一個實質內容在第幾秒;核心主題是否在標題前 20 字內。任一項答不出來,該組作廢重寫。
8. 參考 social-media repo 抽出的 hook 規則(第 1 節)。

### 5.4 結尾

帶走什麼(回收承諾句)→ 一句話輕提 blog → 系列指引(僅系列影片)。不提 podcast;不口頭呼籲訂閱。最後一個場景要留出乾淨的時間與空間給片尾畫面。

### 5.5 寫腳本與查核

**寫腳本時**只守一條:事實來自卡。其他表達完全自由。

**寫完後**由查核員逐句標記並查核:

| 標記 | 內容 | 查核方式 |
| --- | --- | --- |
| `card_claim` | 卡上的事實、數字、主張、實驗結果 | 必須對應到卡上原文;不能更強;附來源類型(設計參數、實驗結果、官方宣稱、作者判斷),主詞依類型寫 |
| `prerequisite` | 教科書等級的前置知識 | 不得碰論文或方法的主張;和卡衝突以卡為準;計入比例 |
| `illustration` | 暖身例子、示意例子 | 列出「例子步驟 → 卡上機制」對照表;數字標「示意」;不得和卡上的機制矛盾 |
| `framing` | hook、轉場、比喻、假設情境 | 程式掃描數字、比較詞、因果詞;掃到就交給使用者在關卡 3 看 |
| `fixed_line` | 使用者寫好的固定句 | 只能填變數,不得改寫 |

- 一句一個標記;混合句拆開。畫面上的字與數字同樣標記查核。
- 只重查被改過的句子;數字先用程式在卡上比對字串,找不到再交給 LLM 判斷。
- 規則卡住好內容時,先換表達方式;仍不行就在審查包列出,由使用者決定。
- 遇到不屬於任何標記的內容,停下來問使用者。

### 5.6 前置知識

- 只限教科書等級、廣被接受的基本 AI 概念(例如 token、embedding、context window)。
- 不碰任何關於這篇論文或方法的說法、數字、比較;不碰較新或有爭議的技術、特定模型的表現。
- 佔整支影片的比例暫定不超過三分之一。

### 5.7 數字與限定條件

- 每個數字三項齊全:量的是什麼、比較對象、限定條件;比例寫出分母。
- 取整不改變意思:31% 可說「約三成」,不能說「超過三成」;方向詞要一致。
- 每個關鍵數字的限定條件,**旁白至少完整說一次**;畫面再補充細節。
- 限定條件不得為了簡潔刪除。

### 5.8 限制段

- 只來自卡;論文作者承認的寫「作者提到」,卡上的評價寫「這篇文章指出」。
- 只放會改變觀眾對結論信任程度的限制,最多 1 到 2 個,約 10% 以內。
- 卡上沒有就整段略過。

### 5.9 系列與命名

- 系列關係:每集獨立可懂、有建議順序。回顧前集最多 1 到 2 句,只重述卡上內容並過查核;只預告已完成或已排定的下一集;系列內容來自同一個卡的系列或同一篇文章。
- 系列名稱以觀念命名,不用論文名;提 2 到 3 個候選給使用者,發布後不改。
- 集數不放在標題開頭,由播放清單決定順序。

## 6. 視覺規則

### 6.1 風格

- 學 3B1B 的原則,不學它的素材:具體先於抽象;每個動作有可辨識的目的;同一概念全片同色;逐步揭露;重用同一張圖;可操作的分布。
- 不做吉祥物角色,不使用 3B1B 的 π 生物或任何素材。
- **鼓勵大膽創意**:每個場景先提 2 到 3 個不同的視覺構想(比喻、構圖、動作語彙),附一句理由,挑一個做;關卡 2 給使用者時,推薦的那個附一張低解析度草圖。大膽指的是怎麼把概念視覺化,不是動得多。
- 比喻只翻譯,不夾帶卡上沒有的事實。
- 研究筆記 `research/A` 有 3B1B 的結構模板、動畫手法清單與反面清單,動畫設計前先讀它的提煉版。

### 6.2 動作紀律(視覺檢查員檢查)

- 每一個移動、變色、出現,都要標明它對應旁白的哪一句;標不出來就刪掉。
- 同一時間畫面只有一個焦點。
- 動畫不演和旁白不同的事。
- 不讓公式或文字無意義地移來移去。

### 6.3 工具

- **工具不定死。** 起點是 ManimCE(0.22.x,MIT),因為目前證據最多。可以嘗試任何工具,包括 Remotion、HyperFrames、WebGL/three.js,以及附錄沒列的工具,不必先問使用者。
- 嘗試要有護欄:限定時間與範圍;寫進 `experiments/` 的紀錄;用同一題材比較。
- 最後用哪個工具,由使用者看比較報告決定。
- 同一專案不混用 ManimGL 與 ManimCE 的 API。
- 安裝或自寫 skill 規範工具用法;專案規則明確寫出禁止事項。
- 附錄有完整的工具資訊。

### 6.4 版面

- 畫面分四區:安全邊界、主畫面區、條件標註區、字幕區(最下方,即使用軟字幕也保留,避免被 YouTube 字幕擋住)。
- 主畫面區用格線定位,起點 6×6。分區與格線由 `lib/` 的輔助函式強制;動畫程式只能指定格子,不得自行填座標。
- 中文換行由輔助函式負責(每行字數上限依字級換算),超過就切行或拆場景。
- 最小字級以「占畫面高度的比例」表示,條件標註也要達到;數值在實驗中用手機實測後填入 `rules/`。
- 畫面文字少而短,多用數字、公式、符號、圖示(英文配音觀眾看不懂中文字)。
- 每場景渲染後抽 1 張低解析度畫面:先用程式查重疊、超出分區;通過後才交給視覺檢查員。

### 6.5 配色

- 背景純黑或接近純黑。
- 同一概念全片同色;公式與圖形中的同一個量同色。
- 每支影片概念色 4 到 5 種(暫定),其他用中性色。
- 頻道固定少數角色色(強調、正確、錯誤、中性);概念色每支影片自己指定。
- 不只靠顏色傳達資訊,同時用形狀、標籤或位置區別。
- 品牌色由 logo 用程式抽出,並對照 social-media repo 的色彩;只用在片頭、縮圖、頻道識別,不當概念色。提案給使用者決定。
- 程式檢查:文字對比度至少 4.5:1(暫定);同概念不跨色;概念色不超量。

### 6.6 字型

- 預設 Noto Sans TC(思源黑體,SIL OFL 1.1)。jf 粉圓、霞鶩文楷 TC、台北黑體(皆 OFL)可試作標題字型。
- 全片最多 2 種:中文字型加公式字型。
- 字重至少 Regular,具體值實驗中定。
- 字型檔放進 `assets/` 並固定版本,附授權文字檔;在 repo 記錄每種字型的授權。沒有 OFL 或同等授權的字型一律擋下。微軟正黑體預設不用;華康、文鼎等商業字型禁用。
- 程式檢查:腳本與畫面中每個字都被字型收錄;顯示的是繁體字形(不可退回其他語言的字形)。

### 6.7 事實型卡的手法

依卡上實際有的數據選手法,並在規劃中寫下理由。

| 手法 | 卡上要有什麼 | 限制 |
| --- | --- | --- |
| 先預測再揭曉(預設) | 可比較的數字 | 揭曉的數字必須是 `card_claim` |
| 具體案例當錨點(預設) | 具體案例 | 案例必須來自卡 |
| 逐項揭露的圖表(預設) | 一組比較數據 | 縱軸從零開始;有比較對象與分母 |
| 前後對照(預設) | 方法前後的結果 | 兩側條件完全一致 |
| 拉動旋鈕(選單) | 多個設定下的結果 | 只畫卡上的點,點之間不畫平滑曲線(除非卡上就是曲線) |
| 拆解(選單) | 總數與各部分 | 加總要等於總數 |
| 熱力圖(選單) | 多條件多指標的結果表 | 色階附圖例,對應固定 |
| 條件逐層加上去(選單) | 數字附帶條件 | — |

不使用「表格停在畫面上念數字」的做法。

### 6.8 論文圖

- 卡上附的論文圖只當參考;一律重新製作,重新設計版面、配色與風格,不逐筆描摹。
- 數字只用卡文字中有的,或圖上有標示的。圖上沒標、只能估讀的:只畫示意並標「示意」,不標精確數字;需要精確數字時停下來問使用者。
- 查核員以能看圖的模型,逐項比對重畫圖與原圖的數值、順序、比較對象。
- 不逐圖標示出處;出處放說明欄(對應的 blog 文章連結)。
- 縮圖、畫面中不使用寫實 AI 人像、真人照片、影片中未出現的公司 logo。

## 7. 聲音規則

### 7.1 TTS

- **主力**:Gemini 3.8 Flash TTS(`gemini-3.8-flash-tts`)加使用者的複製聲音。走 Gemini API 直連、付費層;建立聲音時用 `store=True` 保存聲音 ID。複製聲音能否透過 OpenRouter 呼叫未確認,預設直連。
- **備案**:Gemini 預設聲音(使用者 podcast 現用的設定,開工時從 podcast repo 抽出)。
- 定案前先做第 11.2 節的盲聽。
- 已知限制:同意聲明只有簡體中文版(不行就改用英文版);沒有 SSML 與發音字典;單次輸出上限約 10.9 分鐘(本流程逐句生成,不受影響);論壇有複製失敗與每日請求數 100 的回報。
- 2027 年 1 月 1 日起價格約加倍;Batch 半價。

### 7.2 口語稿

- 每句存兩份文字,以句子 ID 對應:**唸法稿**(給 TTS,例如「百分之三十一」)與**顯示稿**(給畫面與字幕,例如「31%」)。
- 句子短,一句一個重點;台灣口語的繁體中文。
- 英文縮寫首次出現時附全名與一句話說明。
- 維護發音對照表(`rules/`),記錄容易唸錯的英文詞與多音字的改寫方式。多音字唸錯時,改寫唸法稿繞過。
- 參考 podcast repo 抽出的腳本風格規則。
- 語音辨識回聽:把每句音檔轉回文字,與唸法稿比對字錯誤率,超過門檻就重生成(3 次後回報)。實驗證實可靠才保留這道檢查。

### 7.3 對時

Gemini TTS 不回傳時間戳,採旁白先行:

1. 逐句生成音檔(檔名 = 文字、聲音、模型、style 的雜湊);明確指定輸出格式並轉成 WAV,修剪頭尾靜音,量測時長。
2. 只有需要「講到某個詞時觸發動畫」的句子,才做強制對齊(候選:Qwen3-ForcedAligner-0.6B、Montreal Forced Aligner)。沒有繁中評測;必要時先轉簡體對齊再映射回繁體。
3. 場景時長 = 前置留白 + 各句時長與停頓 + 可伸縮的停留時間 + 後置留白,寫進場景清單。
4. 動畫時間只用錨點表示(例如「在第 s3 句的第 2 個詞後 0.1 秒」或「在 s2 到 s4 之間完成」),不寫絕對秒數。
5. 場景各自渲染、最後串接;只有雜湊改變的場景才重渲。
6. 全片時間軸與字幕的絕對時間在串接時才計算;用累計時間換算影格,避免每場景各自取整的誤差累積。
7. 逐句生成和「整場景一次生成再對齊切句」哪個好,由第 11.2 節的試聽決定。

### 7.4 字幕

- 軟字幕:輸出 SRT,不燒進畫面。
- 繁中字幕用顯示稿,不用唸法稿或語音辨識結果。
- 簡體字幕:用 OpenCC 一類工具從繁中轉換,並做地區用語轉換(不能只轉字形)。
- 斷行(起點,依 Netflix 繁中規範):每行最多 16 個全形字(半形英數算半個),每個字幕最多 2 行,每秒最多 9 個字;先在標點斷,再在詞界斷;不在數字與單位、英文單字、專有名詞中間斷。
- 中英之間是否加空格:依 podcast 與 blog 的慣例,全片統一。

### 7.5 音樂與音效

- 只能使用使用者提供的曲庫;不得自行尋找音樂。AI 生成音樂預設不用。
- 片頭、片尾、段落轉換時有音樂;旁白進行時音樂壓到很低或停掉(音量差在第 11.2 節決定)。
- 片頭固定一段識別音樂;段落背景音樂從曲庫輪替,記錄進結構指紋。
- 音效少量,每個音效對應一個畫面事件。
- 用到標 CC 的曲目時,說明欄必須附標示;程式檢查。
- 曲庫只記錄授權資訊進 git,音樂檔留本機。

### 7.6 響度與輸出

- 每句先做輕量的音量一致化。
- 場景音訊保持 WAV/PCM,直到最後一步才編碼(避免 AAC 接縫空隙)。
- 全片串接、混音後,做一次兩段式 loudnorm:目標 -14 LUFS integrated、-1 dBTP、LRA 11;再用 ebur128 驗證。不逐場景正規化。
- 重新取樣到 48 kHz;編碼符合 YouTube 建議(AAC-LC 或 Opus)。
- 程式檢查:響度在 ±1 LU 內、真峰值、取樣率、接縫無空白、頭尾無多餘靜音。

### 7.7 揭露與 C2PA

| 旁白 | AI use 建議答案 | 依據 |
| --- | --- | --- |
| 使用者的複製聲音 | No | YouTube 官方列「複製自己的聲音做旁白」、非寫實動畫、AI 協助腳本與標題縮圖為不需揭露 |
| Gemini 預設聲音 | Yes | 官方沒有明文;選 Yes 只在說明欄展開處顯示標籤,官方說不影響推薦與營利 |

- 每支影片的上傳清單寫明建議答案與理由,由使用者勾選。
- 上傳前檢查最終影片檔是否殘留 C2PA 中繼資料(複製聲音的輸出帶有 C2PA),並回報結果。

## 8. 發布準備規則

使用者自己發布。你只準備素材,不上傳、不呼叫上傳 API。

### 8.1 標題與縮圖

- 使用者在關卡 2 選定開場後,依同一個承諾準備 2 到 3 組「標題加縮圖」,給 YouTube A/B 測試使用(每支影片都做)。各組只換說法,不換承諾。
- 標題:30 個中文字以內,核心承諾放在前 20 字(暫定);前半放觀眾會搜尋的詞,後半放問題或反差;英文術語保留原文;全形標點;少用全大寫與 emoji;禁用誇大字眼。
- 縮圖:直接渲染影片中真實出現的一格高解析度畫面;文字 2 到 6 字,補充標題不重複;構圖簡單、字大;至少 1280×720。
- 在結構指紋記錄開場模式與標題寫法,供成效分析。

### 8.2 說明欄(繁中,另附英文與簡體版)

1. 開頭兩三行:用承諾句改寫的摘要
2. 延伸閱讀:對應的 blog 文章連結;論文資訊只在卡或文章中有時才列
3. 系列影片:其他集的連結
4. 章節
5. 用到標 CC 的音樂時,附標示
6. 使用備案聲音時,加一行「旁白由 AI 語音合成」

不放 podcast 連結。

### 8.3 章節與片尾

- 章節時間戳由場景清單自動算出,章節名稱對應骨架段落;開工時確認 YouTube 的現行章節規則(記憶中為:首個 0:00、至少 3 段、每段至少 10 秒)。
- 片尾畫面由使用者手動設定:放系列或下一支影片,加上訂閱按鈕。最後一個場景依 YouTube 現行規定,留出足夠秒數且畫面乾淨。

### 8.4 多語

- 英文標題與說明、簡體標題與說明:隨繁中版本一起起草,在關卡 4 定稿。只翻譯,不多加說法。
- 簡體字幕:見第 7.4 節。
- 英文:YouTube 自動配音(繁中配英文)。開工時確認開通條件;還不能用時,改輸出英文翻譯字幕(SRT)當備案。

### 8.5 上傳清單(每支影片)

- 影片檔、繁中與簡體 SRT(與備案時的英文 SRT)
- 2 到 3 組標題加縮圖
- 三語標題與說明欄
- 章節
- AI use 建議答案與理由
- C2PA 檢查結果
- 音樂標示是否已附
- 系列播放清單、片尾畫面的設定提醒

## 9. 成效追蹤

用自寫腳本呼叫 YouTube 官方 API 自動抓取,由作業系統每日排程;Claude Code 只在分析時介入。A/B 結果與營利進度每月由使用者手動記錄。依據:研究 L。

### 9.0 架構

- 不用社群的 YouTube MCP server 當主幹:Google 沒有官方 YouTube MCP;社群版很新、使用者很少,有的帶寫入權限,託管型要把授權交給第三方。可以參考 `gomcpgo/youtube_analytics` 的 reach job 排程與第 30 秒留存換算寫法,但不當依賴。
- 可選:用官方 MCP Python SDK 包一個極小的唯讀本地 MCP(3 到 4 個工具,例如 `get_video_snapshot`、`get_retention`、`query_analytics`),供分析對話中臨時查詢。每日抓取仍由腳本負責。

| API | 用途 | 權限範圍 |
| --- | --- | --- |
| YouTube Analytics API v2 | 單支影片快照:留存曲線、觀看時長與百分比、訂閱增減、流量來源、`engagedViews` | `yt-analytics.readonly` |
| YouTube Reporting API v1 | 曝光與 CTR(`channel_reach_basic_a1`、`channel_reach_combined_a1`);全量每日報表(`channel_basic_a3`、`channel_traffic_source_a3`) | `yt-analytics.readonly` |
| YouTube Data API v3 | 影片清單、長度、發布時間;`channels.list?mine=true` 核對頻道 | `youtube.readonly` |

不要加 `yt-analytics-monetary.readonly`:頻道加入營利計畫前請求營收會回 403,也違反最小權限。這兩個唯讀範圍在 API 層級就無法上傳或修改。

### 9.1 一次性初始化(第一支影片發布前完成)

1. 協助使用者建立 Google Cloud 專案並啟用三支 API。OAuth 同意畫面選 External,加入兩個唯讀範圍,按「Publish app」改成 In production(不送審),建立 Desktop app 類型的 OAuth client。
2. `auth.py`:本機授權(`access_type=offline`);授權時要選對品牌頻道;用 `channels.list?mine=true` 核對頻道 ID 並寫入設定,之後每次執行都比對。授權回應若帶 `refresh_token_expires_in`,代表仍在 7 天過期模式,要先改 In production 再重新授權。
3. 憑證(client secret、token)放 repo 外(例如 `~/.config/yt-analytics/`,權限 600)或系統 keychain;`.gitignore` 預先排除相關檔名,並加 secret 掃描。
4. `setup_reach_job.py`:建立 `channel_reach_basic_a1`、`channel_reach_combined_a1`、`channel_basic_a3`、`channel_traffic_source_a3` 四個 job,把 job ID 與建立時間寫入 `data/channel.json`。**必須在第一支影片發布前完成**:曝光與 CTR 只從建立 job 起算,最多回補前 30 天。

### 9.2 每日排程

用作業系統的 cron 或 launchd,每天台灣時間約 18:00 執行 `fetch_daily.py`。不用 Claude Code 的雲端排程(讀不到本機憑證);機器常關機時,改放在常開的機器。

1. 下載所有新的 Reporting 報表(含回補版本),原樣存成 `data/raw/reporting/<報表類型>/<日期>_<createTime>.csv`;同一天以最新 `createTime` 為準做冪等合併。報表 60 天後會被刪除,不可漏抓。
2. 用 Data API 同步影片清單(`data/videos.yaml`:影片 ID、發布時間、長度、標題),每次執行都刷新。
3. 找出發布滿 10 天且沒有 d7 快照、滿 31 天且沒有 d28 快照的影片(Analytics 延遲 48 到 72 小時)。窗口是發布日起 7 天與 28 天,日期一律用美國太平洋時間。
4. 用 Analytics API 抓窗口內的基本指標、流量來源、留存曲線(一次一支);從 reach CSV 加總同窗口的曝光並算加權 CTR。回傳資料的最後日期不等於窗口終點時,延後重試。
5. 寫入 `videos/<影片 ID>/d7.json`、`d28.json`(含 `schema_version`、`fetched_at`、`window_pt`、`data_through_pt`、`view_definition`)、`retention_d28.csv`、`traffic_d28.csv`,然後 git commit。

- 開頭留存:取 `elapsedVideoTimeRatio` 最接近「30 ÷ 影片秒數」那一段的 `audienceWatchRatio`(可能大於 1),同時保存整條曲線。
- CTR 的數值單位(0 到 1 或 0 到 100)與 `channel_basic_a3` 的欄位,第一次拿到 CSV 時確認並寫進 `rules/`。
- 流量來源明細每次最多 25 筆;留存只能逐支查詢。

### 9.3 手動部分(使用者每月約 5 分鐘)

- `data/manual/ab_tests.yaml`:各版本、watch time share、結果(Winner、Performed same、Inconclusive)。Test & Compare 沒有任何 API。
- `data/manual/ypp_progress.yaml`:Studio「營利」頁的精確訂閱數與有效觀看時數(API 的訂閱數會被捨去,觀看分鐘數口徑也不同)。

## 10. token 與使用額度

使用者用 Claude Code 訂閱方案,額度由他所有專案共用。目標每週 1 支,所以影片流程的額度消耗要盡量低。

| 耗額度的地方 | 規則 |
| --- | --- |
| 背景資料 | `CLAUDE.md` 精簡;細節放 skill,執行到該步驟才載入;研究報告不載入,只讀提煉後的規則 |
| 看圖 | 先用程式檢查,通過才送圖;每場景只送 1 張低解析度畫面 |
| 查核 | 只重查被改過的句子;數字先用程式比對字串 |
| 動畫除錯 | 只改出錯的場景,不重寫整個檔案;錯誤訊息只帶相關的幾行 |
| subagent | 只給它需要的輸入;只回傳結構化的簡短判定 |
| 長對話 | 狀態都寫在檔案裡;每支影片或每個大步驟可以開新對話接續 |
| 模型 | 規劃、暖身例子、腳本用較強的模型;標記、格式化等機械性工作用較便宜的模型(若可為 subagent 指定模型) |
| 重做 | 依靠關卡 2 在渲染前擋下錯誤,避免整批重做 |

**量測**:每一步記錄用量;拿不到用量資料時,至少記錄重試次數、送檢圖片張數、渲染時間。第一批 2 到 3 支影片完成後,整理每支影片的額度、TTS 金額(約 US$0.14 一支 10 分鐘)、渲染時間、使用者審查時間,找出最貴的步驟並提出優化方案。每支影片的預算上限,在那之後和使用者一起定。

## 11. 實驗計畫

開工第一步完成後做兩個實驗,都只測試、不發布。每個實驗限定時間與範圍,結果寫進 `experiments/`,最後寫成比較報告交給使用者決定。

**落地順序**:準備(第 1 節)→ 實驗 11.1、11.2 → 第一支試片 → 存 2 到 3 支緩衝 → 每週發布。

### 11.1 工具比較實驗(視覺)

- 題材:「Attention 機制在做什麼」,30 秒、3 個場景(詞變成方塊;方塊間連線粗細代表權重;公式 softmax(QKᵀ/√d)V 逐項高亮)。測試專用,不受「知識不超出卡」限制。
- 自選 2 到 3 個工具各做一次(ManimCE 為起點)。選做:挑一個需要空間感的場景(例如詞向量在空間中的位置),用 three.js 做一版。
- 檢查項目:

| 類別 | 檢查 | 標準 |
| --- | --- | --- |
| 工程 | 環境可重現 | 一個指令裝好 |
| 工程 | 確定性 | 同一份程式渲染兩次,每格雜湊相同 |
| 工程 | 錯誤自修 | 故意誘導錯誤 API,3 次內修好或事先被擋下 |
| 繁中 | 字型 | 無缺字、無簡體字形、小字級字距正常 |
| 繁中 | 換行 | 40 字說明自動切行且不超出安全區 |
| 版面 | 自檢迴圈 | 最多 2 輪就沒有重疊與裁切,使用者看圖也同意 |
| 公式 | 呈現 | 能逐項出現、逐項變色 |
| 風格 | 動作紀律與配色 | 通過第 6.2、6.5 節的檢查 |
| 效能 | 渲染時間 | 記錄 1080p30 的實際秒數,換算每分鐘影片要幾分鐘 |
| 人 | 手機實看 | 看得清、看得懂、不像投影片 |

- 本實驗同時校準:格線大小、主要文字與條件標註的最小字級、字重、概念色上限、對比度門檻。
- 報告寫明推薦工具與理由;是否採用由使用者決定。

### 11.3 第一支試片

- 選題:機制型卡、有清楚的小例子、前置知識少、長度約 5 到 8 分鐘、不需要拆集。緩衝的第二支選事實型卡。
- 完整走完九個步驟與四個關卡。
- 成功標準:流程跑完且失敗時有回報、中斷能接續;關卡 3 沒有查核漏掉的事實錯誤;使用者判斷看得懂、想看完、帶得走一句話;一位外部觀眾看完能用一句話說出學到什麼;記錄額度、渲染時間、使用者審查時間。

## 12. 每支影片發布後的回顧

使用者發布一支影片後,會請你回顧這次的執行過程。

5. 回顧要簡短:每週都會做一次,只改確實需要的地方。
